## Platform

web

## Users

Primary: deployers, privacy-conscious people and, on equal terms, AI agents, who hold a wallet, browse the catalog on enclave.host, fund a deployment, and use the running app (private LLM chat, image generation, game servers). They come because they need compute on data they refuse to show a provider, and they judge the product by whether that promise is credible, effortless, and honestly scoped to the host they land on.

Secondary: developers/publishers who build `wasi:http` Wasm apps once and publish them to the on-chain catalog for per-hour fees. Tertiary: hosts/operators who register hardware they own and earn by claiming work; confidential hardware sells the strongest tier, other machines are listed at the level they can prove. Design serves the deployer journey first; developer and host paths stay one click away, never in the way.

## Product Purpose

Enclave (enclave.host) is a verifiable compute platform built around one architecture: one portable app bundle and one versioned domain contract; an OS-independent hardware-isolation security contract (per-app hardware isolation, the ordinary host operating system excluded or deprivileged by a smaller measured trusted layer, measured identity, attestation, key and traffic binding, fail-closed verification, lifecycle cleanup, portable operation across backends); equivalent VBS-style implementations of that contract being built on supported Windows and Linux hosts; and confidential hardware, which adds protection from the machine's operator and memory encryption without changing the app contract. A host is listed only at the level it proves with verified evidence, and today confidential hardware is what proves one. The infrastructure is designed to depend on the company as little as possible. Paid per second from a wallet on Base. It exists so that using powerful software on sensitive data does not require trusting whoever runs the hardware, and so that the buyer can always tell which guarantee they bought. Success means deployments funded and running by strangers who verified the claim rather than took it on faith.

## Positioning

Lead claim (user-confirmed): **compute that cannot see your data**, the privacy outcome itself. The hero states it as the architecture delivers it: an app runs in a hardware-isolated domain the machine's ordinary operating system cannot see into, with identity measured and keys and traffic bound to that measurement, verified before a byte is sent; on confidential hardware the machine's operator is locked out too. Today every listed host is confidential hardware, so the claim is true of every host a deployer can land on; copy must never extend it to a machine that has not proven it.

Four pillars, in this order, carry the story on the homepage (updated 2026-09-23): **portable apps** (one bundle, one domain contract, every backend), **one isolation contract** (OS-independent; confidential hardware adds to it), **verifiable execution** (client-side chain of trust), **independent infrastructure** (public contracts, content-addressed bundles, public source, independent hosts; the goal is to outlive any one company or domain, and the parts still on company servers are listed honestly). The public marketing copy describes the full target architecture as the product, in direct present tense (what Enclave does, how hosts, apps and GPU isolation work, what customers receive), with no roadmap, status or readiness framing ("we are building", "being built", "planned", "experimental", "future", "eventually" never appear in market copy). Empirical proof and current deployment facts stay exact in clearly technical contexts: the dated "Engineering evidence" note at the end of Develop > Architecture, the live fleet panel, and docs/site-claims-2026-09-23.md.

Supporting mechanisms (never lead, always available as proof): the full chain of trust is verifiable client-side in the browser before a byte is sent (CPU attestation quote → measured image → Sigstore-logged release → this repo's commit); access is wallet-native ("If it can sign, it can compute.", no accounts, no KYC); the marketplace is non-custodial and on-chain (catalog, per-second billing, publisher fees forwarded without custody).

No readiness taxonomy on the public site: the words available / experimental / planned, status badges, and status boards are not how the site is organized (removed 2026-09-23 at the owner's direction). One dated engineering note (Develop > Architecture > "Engineering evidence") records what has been demonstrated, what has not, and what is attached; that note, the fleet panel and repository documentation hold milestone evidence (M1 to M4b, the consumer machine's gaps, the Shield engine's deployment) and never define the narrative or the level names.

## Operating Context

The site is a static, IPFS-published app (LWC-style web components, soft-nav router) at enclave.host: catalog browsing, wallet connect (passkeys + SIWE), Stripe Checkout for credit, one-click deploy from an app's card, dashboard with live provisioning output, per-deployment settings tabs (config, model volumes, protection, relay, secrets, domains) and in-browser attestation checks, host console, an architecture page (protection levels, verification, research status, independence, the status board), developer docs with OpenAPI reference. Deployed apps serve at `https://<id>.app.enclave.host` or on customer domains with certificates minted inside the enclave. The same platform is driven by the `enclave` CLI and by coding agents via the MCP server at mcp.enclave.host — agents are first-class users, not an afterthought.

## Capabilities and Constraints

Capabilities (available): Wasm (`wasi:http`) apps from the on-chain catalog, run on the confidential Linux fleet and, interpreted, on the Windows enclave node; GPU inference via `wasi-nn` (GGUF/llama.cpp, ONNX, stable-diffusion) on fractional GPU slices inside the confidential VM; attested read-only model volumes; raw TCP/UDP behind an SNI relay; per-deployment dedicated IPv6; deployment secrets; encrypted volumes; per-deployment WAF; USDC (EIP-3009) and ETH funding, metered per second, self-serve cancel refunds the contract-held remainder; custom domains; Android shell app with QR pairing; self-hosted confidential servers (metal); free self-hosting of your own apps.

Protection levels are OS-neutral and there are exactly two, each a set of guarantees a host proves with evidence: **the isolation contract** (per-app hardware isolation; the ordinary host OS excluded by a smaller measured trusted layer; measured identity; attestation rooted in something the host does not control; keys and traffic generated and terminated inside the domain; fail-closed verification; lifecycle cleanup; portable operation) and **confidential hardware**, which is the same contract plus memory encryption and protection from the machine's operator, with the report signed by the processor and chained to the silicon vendor. Every host listed today is confidential hardware; no host is listed at the base level until a backend passes the common acceptance tests. Windows and Linux appear only as implementation detail: equivalent VBS-style backends being built to one contract. A machine that meets part of the contract (a test-signed trusted layer, a key or traffic path on the host side, a launcher-signed report, host-readable memory) is implementation evidence, never a weaker sellable level, and is not presented as available; the attached consumer node is exactly that. There is no plain tier: ordinary virtualization with the host OS in charge is a lab control in the isolation research, and Enclave does not build, list, route work to, or market it. Eligibility for tenant compute is derived from evidence the relay verified at attach, never from OS identity or a self-reported tier string (relay/api-relay.js computeEligible, mirrored in site/js/core/pricing.js computeEligibleOf). Physical attacks on the memory bus are outside what confidential CPUs defend, and the site says so where it matters.

**Enclave Shield** (named 2026-09-23) is the umbrella name for Enclave's proprietary protection technology for machines that lack confidential-computing hardware. It combines two components, and marketing copy may describe them together as Enclave Shield while the explanation keeps them distinct: (1) the **host isolation component**, the OS-neutral per-app CPU/host isolation layer with VBS-like protections (a smaller measured trusted layer keeps the ordinary OS out of each app's hardware-isolated domain; on Windows VBS and Hyper-V hardware isolation with a paravisor-owned partition, on Linux a measured layer below a deprivileged host kernel; one bundle, one domain ABI, one security contract; no plain or software-only fallback tier), and (2) the **GPU offload component**, masked and verified offload for any GPU that does not support, or is not operating in, confidential-computing mode (the card sees masked inputs, returns results verified before use, never receives plaintext protected state). On a machine without confidential-computing hardware both components together are Shield protection. On a confidential CPU host whose GPU is outside the confidential boundary, the GPU offload component still applies; a GPU in supported CC mode sits inside the boundary and does not need it. Shield does not give the separate guarantee a confidential processor gives, that the owner cannot inspect data, and copy says so. The GPU rule: within Enclave's architecture Shield's offload is the only supported way to expose a non-CC GPU, on any host; admission reads the card's protection mode from explicit verified evidence, never `teeCpu`, the host OS, whether the CPU is confidential, or the absence of a field, and fails closed. That rule is stated as product behavior in market copy; the runtime carries no card-specific gate yet (a box without confidential-CPU evidence sells nothing, card included; a confidential box's card is offered as before), and no rebrand may add an unverified admission signal or make current GPU capacity disappear or become newly trusted. Shield is a named component of the market narrative (homepage lede, pillar card, contract card and GPU note, Develop > Architecture section `#shield` with component subsections and `#shielded` / `#masked-offload` alias anchors, host page, ticker, footer), in present-tense product language, with deployment facts in the evidence contexts above.

The adjective "shielded" remains the technical term in code, paths, wire fields and engineering docs for the offload mechanism (the `shielded/` directory, `availability.shielded`, the shielded worker unit and its shared-memory paths, the user-agent string), a compatibility surface never renamed after the brand. Never conflate Shield's product rule with the masked-offload performance research on large models (the mechanism is Shield's, the figures are research and unpublished) or with the orange pVM CPU phone tier.

The phone tier (direction of 2026-09-23): the Pixel TPU path is not a product tier (it demonstrated about 2 tok/s against a 15 tok/s floor for exposure) and TPU or accelerator acceleration is never marketed. Its replacement under construction is the **pVM CPU** tier for Pixel 10 and Pixel 11: CPU-only inference inside the protected VM, pVM attestation verified at attach, capability-based admission. Its UI identity is the amber ("orange") badge `pvm cpu` everywhere it appears (fleet panel, architecture tab), its copy is future tense ("we are building"), it claims no Pixel 11 runtime validation and no availability until the pVM session supplies reviewed evidence, and it is distinct from the OS-neutral server isolation contract: a phone row is never sellable app capacity.

Not to be claimed without new evidence: per-app hardware isolation in production; an attested monitor on the IGVM/M3b path (the launch digest covers SVSM and firmware, not the monitor image); M4a as shipped or as more than one-guest-per-app (it is measured and rechecked, not in the product); M4b as measured (in progress); hardware app-vs-app isolation at scale via planes (hardware caps it at 2 to 3 apps per guest); a confidential GPU host or a self-hosted server as currently attached unless the live fleet panel shows one (neither was attached on 2026-09-23; metal0 has been off since 2026-09-14); any public performance number for shielded inference or phone accelerators (each needs model, hardware, protection mode, conditions and checked evidence, and unstable numbers are omitted); permissionless hosting as open today (admission is by a measurement allowlist); Windows hosts as confidential or host-blind; native CreateEnclave as the Windows roadmap (the direction is the partition-per-app backend); a plain or ordinary-virtualization tier as supported, planned, or a fallback.

Constraints future work must respect: the site is static — no server-side rendering or per-user backend for site pages; inline scripts are CSP-hash-synced at deploy (a stale hash silently blocks a page's script); long LLM responses must stream (non-streaming dies at ~180 s at the proxy); the platform never takes custody of user funds; contract changes are effectively frozen by the EIP-170 size wall and one-shot governance, so product promises must not assume cheap on-chain iteration.

- Slogan: **"If it can sign, it can compute."**

## Product Principles

1. The privacy outcome leads; the mechanism supports. Say "cannot see your data" before any word of attestation vocabulary.
2. Never ask for trust the user could verify: every claim should sit one click from its live proof.
3. Deployer journey first: browse → fund → use, with a wallet as the only identity.
4. Anything holding a key is a customer — human or agent; no flow may assume a human.
5. Real proof only: name eyesoff.ai or stage live verification; never manufacture social proof.
6. Protection is a contract a host proves, never a name for an operating system: "cannot see your data" is said only where hardware enforces it and a verified report says so, and a machine that proves part of the contract is not listed at all. Enclave Shield is the name for how that contract is met without confidential hardware; its two components are always explained separately.
7. One package, many hosts: portability is a promise about the deployer's build, never about identical guarantees on every backend.
8. Independence is a direction with an honest inventory: name what is already on public contracts and content addressing, name what still runs on company servers, and present the rest as proposals until code establishes it. Existing payments and contracts are not described as being replaced.
