1. ROOT REVIEW FINDING: CONFIRMED. The draft lets a banned operator's endpoint be served through another advertiser.
Draft design: a `native-control` (kind 9) service-index ad; strict admit===true for the ADVERTISING operator; a TLS
handshake to the advertised IP:443 that verifies the leaf under the native CA for the name.
Defect: the policy decision and the TLS proof are not bound to each other. The certificate binds a key only to DNS names.
Any unbanned operator can advertise a banned operator's IP. The advertiser passes the policy check, and the banned
operator's own valid leaf passes the TLS check.
Reproduction: draft-6e46c06d/test/native-control-substitution.test.mjs (worktree of my clone at 6e46c06da). It runs the
real readServiceIndex over two agreeing in-process RPCs and a real TLS endpoint with a production-profile leaf (DNS SANs only).
  Scenario: banned operator Y (0x66…) and unbanned advertiser X (0x11…) both advertise https://44.0.0.6/.
  Result (logs/subst-draft.out, queue 256 MiB, exit 0, 1/1 pass, so the defect was reproduced):
    - Y's own ad was refused;
    - api and mcp routes were both [44.0.0.6], attributed to X;
    - the leaf's subjectAltName was exactly "DNS:api.enclavehost.eth, DNS:mcp.enclavehost.eth".
  The draft's earlier tests banned only the advertiser, so they did not cover this case.

2. DOES EXISTING SOURCE OFFER AN AUTHENTICATED ENDPOINT -> HOST/OPERATOR BINDING? No. Checked in 6f2c7da4:
- Native CA leaves (work/control-vm/renew-native-cert.py) are issued from ONE shared services.key on the minipc control VM.
  They carry DNS SANs only: api, mcp, get, ipfs and sia .enclavehost.eth. No operator, registry id or endpoint is named.
- The measured control statement (metal/guest/measured-control.mjs) binds only keys.controlTls (spkiSha256) to the
  operator and publicUrl. verifyMeasuredControl checks that the TLS peer at the control front is that attested key.
  - The SNI certificate for platformApi.hostname is a separate key file (/run/measured-control/platform-api/webpki/key.pem).
    No statement field names it.
  - With no SNI file present, the front serves the attested control certificate, which does not chain to the native CA.
  So no measured guest can present a native-CA leaf that is attestation-bound.
- EnclaveRegistry endpoints are operator self-claims (host id = keccak256 of the exact bytes). Any operator can register
  any IP in another string form. An IP match is therefore not a proof of who serves it.
- Platform policy semantics (network/platform-host-policy.mjs judgeHost): deny entries may name registryId, chipId,
  operator, owner or endpoint. decideOperators judges only {operator}, so an operator ban does not follow that operator's
  endpoints. An admin endpoint ban ("https://<ip>", exact string) blocks one address string. It is an IP denylist, not
  serving-host admission.
- Service-index descriptors are the advertiser's own statement. They cannot name a key the advertiser does not control in
  any binding way, because the SPKI is public.
Conclusion: under the current protocol, a native control endpoint cannot be tied to an admitted host. As root directed, the
final source refuses control routing. It does not introduce a bypass.

6. MISSING PROOF: what production needs before control routing can be turned on (no new contract)
Required property: the key that terminates TLS for api/mcp.enclavehost.eth at an address must be bound, by an existing
authority, to a registry host. Discovery then judges THAT host fresh (gate.decide({registryIds}), admit === true, strict as
in judgeRelayOperators/hostAdmissions), never the advertiser. The address must lie outside the DO failure domain, and the
route must live 60 s or less.
Two options, smallest first. Neither is implemented here; both need root and admin decisions.
 A. Native-CA certificate profile (no image change, existing admin trust root).
    - The CA holder issues a native leaf only to a host it admits, and names that host's registry id in the leaf.
      Example: a URI SAN "enclave-registry-id:0x<64 hex>" alongside the DNS SANs.
    - Discovery verifies the leaf under the native CA, as the draft already did, then reads the id from the VERIFIED leaf.
    - It judges that id under the platform host policy and requires the ad's operator to equal the registry operator at
      the same agreed block.
    - Missing today:
      - the profile itself;
      - per-host leaf keys, replacing the one shared services.key;
      - an issuance step in the CA tooling;
      - a fail-closed reader for that SAN.
    - Ban latency is the policy refresh, at most 60 s. Leaf validity (7 days today) bounds the CA side only.
 B. Attested key (stronger, needs a measured image change).
    - The measured control front presents, for SNI api/mcp.enclavehost.eth, a native-CA leaf issued over the ATTESTED
      keys.controlTls public key. The CA can certify the statement's SPKI without the private key leaving the guest.
    - It does so on the native port (443), routing Host api.enclavehost.eth to the platform API and mcp to the MCP route.
    - Discovery then pins the leaf SPKI, runs the unchanged verifyMeasuredControl at that endpoint (operator, publicUrl,
      registryId), and judges the registryId as in option A.
    - Missing today:
      - measured-control.mjs/gsup support for serving a native leaf over the control key, plus a second hostname route;
      - an image rebuild (root review);
      - the CA issuance step over a statement SPKI.
Until one of these exists, deploying the final file turns native api/mcp resolution OFF. It does not move it.
