# Public RPC / verifier interface gap

B's actual witness gateway requires eth_getProof for fresh account/storage witnesses and eth_getBlockByHash for authenticated ancestry/historical blocks. S's current role was intentionally scoped to browser methods and rejects both. Root exercised the real HTTP role, including the previous own-property correction, and both calls returned-32601 before any backend call. Actual verifier WITNESS_METHODS was imported, and exact source hashes/commits are recorded. This is an interface-level counterexample, not a complete Reth/Helios deployment test.

The browser role by itself therefore cannot be the supported fresh-proof source for remote verifier guests. This is a composition gap relative to the overall goal, not a claim that S violated its narrower browser task. Next S scope should expose a bounded own-node proof/header path through supported host ingress, preserve strict validation/limits/admin gating, and test the actual verifier against it with real Reth. Include any full-block shape needed by the actual historical Helios path; do not loosen all RPC methods or trust returned proof contents. No public provider fallback.

Related completion gate: browser note explicitly leaves wallet broadcast on the wallet's own RPC and passkey user operations on their own bundlers. Before claiming complete public-RPC replacement, verify those paths can select supported independent services. Current S browser method list lacks common fee metadata; actual wallet/client requirements must be verified before proposing the minimum compatibility extension. This review did not interact with MetaMask, change networks or verify a particular wallet implementation.
