2. MECHANISM (source; each step is the line that runs)
  a. A dependency outage used up the readiness window.
     shield-secrets.mjs:43-51: the host-side courier retries secret delivery every 15 s, only while the VM's status is
     'starting', and only logs failures. The guest waits for its secrets and stays 'starting'.
     The courier keeps this state in memory only (done/retry, :7). host.mjs never consults it.
  b. The deadline treats "not ready" as the app having ended.
     isolation-lifecycle.mjs:51: the deadline is 300 s for enclave-catalog-bundle/6|7 derivations. The 300000 in the reason
     shows this app uses one of those derivations.
     isolation-lifecycle.mjs:126-135: at the deadline it retires the VM, confirms it is gone, and returns
     {action:"failed", leaseFree:true, ended:true}. It cannot tell "the app is broken" from "an external input never arrived".
  c. Respawn was off for this id.
     host.mjs:1328-1330: respawn applies only if cfg.isolationRespawn or this id is in cfg.isolationRespawnIds
     (env ENCLAVE_ISOLATION_RESPAWN / _IDS / _DELAY_MS, agent.mjs:183-187). The recorded reason has neither the respawn
     suffix (:1347) nor a "provisioning" respawn reason (:1344, :1361, :1377). So that branch did not run.
     This is evidence from the exact reason string; I did not read the NucBox environment.
     It was not the reboot-recovery path either: #rebootHold's wording (host.mjs:2709) is absent from the reason.
  d. The give-up is persistent.
     host.mjs:1403-1404 -> #giveUp -> #giveUpOnce (2601-2645):
       :2625 records status failed; :2626 blocked.set(id, why); :2627 stops tracking the id and saves it to disk;
       :2634-2638 releases the lease on chain (one transaction, matching the 08:55:53 log).
     host.mjs:254-258: the blocked map is persisted and reloaded across restarts by design.
     host.mjs:2063: the ledger scan skips blocked ids. host.mjs:753-757: any non-forced consider() re-records
     "failed" with the stored reason. host.mjs:759-761: only a forced claim-hint clears the entry.
     The comment at host.mjs:1322-1324 already says this is "effectively permanent" for an owner-only NucBox deployment.
  e. The pin means no other host can take it.
     chain.mjs placementRefusal (deployed chain.mjs:481-486) returns "Pinned to host <NucBox>; fallback is disabled." on
     every other Windows host. Linux hosts return the same text (supervisor.js:2125). NucBox has it blocked, and every other
     host refuses it by pin. Result: failed indefinitely, with no automatic exit and no gas spent.
  f. Why the dashboard shows another host's pin refusal.
     Actual: after the release, the ledger row has no runner, so the dashboard row reads "queued".
     site/components/deployments/deployments.js:1704-1722 (_probeWhy) sends a non-forced POST /v1/claim-hint for queued
     rows and displays a returned reason.
     Inference (I did not read the relay's fan-out/merge code): the displayed reason is a non-NucBox host's
     placementRefusal, not NucBox's own blocked reason. WHY_TERMINAL (deployments.js:318) does not match "Pinned to host",
     so the dashboard shows it as an ordinary dim "fleet: …" line, which hides the actionable cause.
