PACKAGE A (manager; works with the CURRENT guest image)
  Rule (cpu-share.mjs; units are Msvm_ProcessorSettingData percent/1000 per VP):
    entitlement = floor(pool*share*1e5 + 1e-6)
    VPs         = max(catalog vcpus, ceil(entitlement/1e5)), and <= pool
    Limit       = Reservation = floor(entitlement/VPs), and >= 1000
    granted     = VPs*Limit (never over the entitlement; under by fewer than VPs units)
    On 16 LP: 1% -> 1 VP @16000 | 13% -> 3 @69333 | 17% -> 3 @90666 | 21% -> 4 @84000 | 25% -> 4 @100000.
  Call chain:
    1. Manager.spawn takes the same body.cpuShare that sizes RAM (the witness keeps its exact current launch) and passes
       backend.start opts.appCpu.
    2. WmiHyperVLauncher defines the VM with New-CustomVM -VpCount VPs (the define script is UNCHANGED).
    3. The new CMD.processor script runs on the never-started VM (must be Off and ours by its Notes). It calls
       ModifyResourceSettings only when the values differ, re-reads VirtualQuantity/Limit/Reservation/AllocationUnits
       plus the Get-VMProcessor Count, and throws on any mismatch. checkProcessor states the same check again.
    4. Any failure removes the VM by its Id.
    5. startAndRead, then wmiserve --vcpus VPs.
  Pool: the node's own rule, NODE_VCPUS || os.cpus().length (16 on NucBox). main.mjs refuses to start (exit 2) on an
    explicit value that is invalid, above 1024, or set without NODE_APP_RAM_GB. Preflight reads Hyper-V
    LogicalProcessorCount and keeps the last good value. If the pool is unknown or larger than that count, real
    deployments get 503 and /health canStart is false.
  Admission: sum(granted for held domains, witness = 1 VP) + new <= pool*1e5, else 507. Recovered partitions => 503.
  Metadata:
    /health.cpu: rule, poolVcpus, source, hostLogicalProcessors, allocatedUnits, freeUnits.
    record.cpu: entitlementUnits, vcpus, limit, reservation, grantedUnits, readback, guestOnlineVcpus (console
      "MON ... vcpus=N"), appCpuPercent, appCapUnits, realizableUnits, blocker. An unobserved online count counts as 1 VP.
  With the current image the monitor's cgroup caps the app at the catalog cpuPercent (1 CPU). The record states this,
    but per root's ruling it is NOT an acceptable end state.
  ENCLAVE_GUEST_CPU_ALLOWANCE (default off) is the manager half of B. It sends ceil(granted/1000) only when that is above
    the catalog cpuPercent. A missing or mismatched echo is refused, never served. The GPU launcher has it forced off.

PACKAGE B (guest CPU allowance; root-requested)
  Monitor allocatedPolicy: a bundle load's cpu RAISES the domain's cgroup cpu.max when
    catalog cpuPercent <= cpu <= online CPUs*100, and refuses it otherwise. No silent ignore, no lowering, no unbounded
    override. The manifest, AppID and report policy are unchanged, and the load answer echoes cpuPercent.
  wmiserve --app-cpu (at most 100 per VP) is sent as the load's cpu. wmiserve refuses to serve, and destroys the domain,
    unless the echo matches; it prints cpuPercent and memMiB on its load step.
  Compatibility:
    - Old wmiserve: it ignores --app-cpu and states no cpuPercent, so the manager refuses the start.
    - New wmiserve on an old monitor: the echo is 100, so wmiserve refuses.
    - The m3ctl dev tool sends cpu equal to its own bundle policy, which is accepted.
