# Custody canary launch package

This packages the corrected r2 image and capture-only host helper. It does not launch a VM, read the registry key, open ports, sign, send, or mark `G.launch` complete. The original custody service and sealed state remain outside the package.

After the plan's prerequisites pass, root supplies `pins.launch` with the exact reviewed `ovmf` and `qemu` absolute paths, `qemuSha256`, private `registryKeyFile`, and unused `hostPort`/`mgmtPort`. `pins.custodian.manifestFile` must be the exact r2 manifest; `endpoint` must be the dedicated public HTTPS origin. `pins.custodian.captureDir` must be the planned package's `capture` subdirectory, so the later bounded sender consumes this guest's intent. The client repository must match its source pins. The template deliberately lacks executable launch settings.

Run `node driver/cli.mjs launch-prepare --pins <reviewed-pins.json> --step G.launch`. Save the returned package digest in the operator evidence. The command creates an exclusive private `r2-launch-<runLabel>` directory under this run's private directory. It never overwrites a package. Interrupted preparation leaves the partial directory for inspection; do not reuse it blindly or remove a directory holding sealed state or a captured intent.

Run `node driver/cli.mjs launch-check --pins <same-pins.json> --step G.launch --confirm <saved-digest>` immediately before the separately guarded root launch. This rechecks the image, firmware, QEMU, Node executable, copied host, resolver hooks, capture dependencies, configuration and private permissions. State and capture directories must be empty. A changed pin cannot silently bless an old package. The verifier's `requireFresh:false` API is only for inspecting retained files during explicit recovery; the CLI does not offer it as a fresh-launch bypass.

The package fixes the guest at two vCPUs and3072MiB, original vault0xE486, direct ingress, metal0 registry identity and genesis creation. Its host copy has no automatic submitter. It contains no submitter key or inherited environment. Launch only the exact Node argv and explicit environment in the package; do not merge the current environment. The resolver maps imports of the copied host to the reviewed repository. The capture module records one private durable intent and returns503 until a separately budgeted transaction confirms.

The runtime supervisor now checks fresh accepted host authority; a 5120MiB memory cap and zero swap in both systemd and the live cgroup, a 16GiB available-memory floor plus a 2048MiB recipient reserve; protected-process inventory before and after; unused ports before start and exact exclusive loopback listeners afterward; runtime process/config provenance; before and after launch. A separately verified ingress route and fresh AMD-rooted quote are still needed. `launch-check` proves file consistency only; `launch-inspect` collects actual Linux runtime observations. The `record G.launch` path explicitly refuses manual observations. Only the combined `launch-verify` command described below can journal a pass.

Rollback before genesis: stop only the new identified canary process tree using the guarded supervisor; preserve its private state and captured intent. Do not touch original custody or tenant processes. After any creation send, reconcile the bounded sender's original journal and transaction before any restart or retry; never create a replacement committee merely because a reply was lost. Full live launch/stop and outage procedures remain unfinished and must be completed before production lifecycle testing.


## Runtime commands

After accepted host authority and all plan prerequisites are satisfied, `launch-start --pins <pins> --step G.launch --confirm <package-digest>` creates exactly one private runtime record and starts one timestamped transient user service. The record is fsynced before systemd is called. A failed or timed-out start remains uncertain; run `launch-inspect` against that same record. Repeating start is refused even if the previous service has exited. These commands have not launched the production canary.

The service has MemoryMax=5120MiB, MemorySwapMax=0, TasksMax=64, RuntimeMaxSec=1800, no automatic service restart, and KillMode=control-group. Its environment is explicitly cleared; no submitter key is inherited. Host console output is discarded. Guest stdout/stderr are privately captured as described below. The transformed host forbids automatic QEMU restart; inspection also pins its first observed process identities and refuses later restart or PID reuse. Source files, exact Node/QEMU arguments, environment, parentage, cgroup membership, actual kernel memory limits, OOM counters, socket ownership, all pre-existing QEMU processes and the original custody/guestd/metal services are checked. The memory floor is sampled at start and inspection; this is not a continuous host-memory watchdog.

`launch-stop --pins <pins> --step G.launch --confirm <package-digest>` stops only the recorded service invocation and refuses a replaced invocation or a protected process inside its cgroup. It works even if the canary's health, memory counters or source-file checks fail. It never deletes sealed state or capture records. A failed post-stop protected-service check is reported as a failure, not preservation success. No process-name kill or arbitrary PID kill is used. Stopping after a transaction still requires reconciliation before any recovery launch. The 30-minute runtime is deliberate: do not begin until the rest of the short canary sequence is ready. Recovery/restart and outage commands are still incomplete.

The fake process/systemd tests establish decision behavior only. A separate read-only Linux inventory on October24 at02:32:49UTC found four running QEMU processes, the three protected services active, and24871MiB available. It did not start a unit or demonstrate a canary cgroup on hardware. The combined launch gate is now wired, but has only been tested with fixtures. Never substitute runtime-verified or a launch-gate pass for a production lifecycle pass.

## Combined launch verification

`launch-verify --pins <same-pins.json> --step G.launch --confirm <package-digest>` collects actual runtime and restricted ingress evidence, fresh accepted host authority, and independently challenged AMD-rooted SNP quotes through both the runtime-owned loopback management socket and the public origin. Both quotes must name the exact same identity, encryption key, physical chip hash, registry, endpoint and reviewed r2 measurement. The public origin remains inside the signed machine binding even when the local transport uses loopback. Local transport allows only the exact evidence POST, with redirects forbidden. Raw reports, signatures and chip identifiers remain in memory.

The command then collects authority, ingress and runtime evidence again. A changed owner, route binding, service invocation, process identity, stale quote or collection exceeding120seconds refuses. Only passing all checks records the three G.launch prerequisites; manual record cannot bypass it. Source pins are checked by the CLI first. This proves a bounded launch observation, not continuous availability, decentralized routing, state rollback protection, committee creation or secret release. Existing authority/ingress/resource prerequisites still prevent running the non-executable template. No production launch was performed while implementing this command.


## Explicit child lifecycle and later recipient preservation

The capture-only copy also replaces the original host's internal QEMU relaunch handler with `watchCanaryGuest`. Unexpected exit (even zero) or spawn failure ends the host; it cannot silently create a replacement guest while an outage is being observed. The launch package now pins this helper as an input. Existing package digests change and must be re-prepared before launch; nothing already deployed is changed by editing these sources.

The stop operation protects every VM present immediately before the stop, not just the initial launch baseline. Its only permitted VM is a single QEMU child of the recorded canary host in that exact cgroup. Every other VM, including the later recipient, must remain byte-for-byte identical in process identity afterward. A service-health failure still prevents a preservation claim but does not prevent stopping a positively identified owned canary.

The old generic O.restart recorder was not a restart verifier: it accepted release logs without checking the restart. That path is now refused. Dedicated outage/recovery orchestration, evidence collection and live verification are still required. Historical startup-only hardware evidence cannot stand in for the production secret lifecycle matrix.


## Private guest output (October 24)

New packages include a fresh 0700 logs directory and pin private-log.mjs. The transformed host uses piped QEMU stdout/stderr; host console output still goes to the unit's null output. Captures are 0600 exclusive files with a combined 4 MiB bound. A second launch cannot overwrite an earlier generation. Failures are terminal and completion metadata is distinct from an interrupted capture. inspectCanaryRuntime now checks guest-stream metadata against the actual host generation and file identity; it exports no stream contents. Existing prepared packages will fail the changed digest check and must not be silently reused.

The raw files are sensitive local evidence. Do not copy them to reports, Git, a relay or tool output. A matching hash is only local provenance: hardware attestation and challenge/HMAC verification remain separate requirements. A host that exits before streams close leaves incomplete evidence; no complete-capture or rollback claim follows from a partial prefix. Explicit recovery must select a new log generation while retaining the original logs and sealed custody state; that recovery procedure is still unfinished.


## Live stopped-state observation and recipient preservation

`launch-stopped --pins <pins> --step G.launch --confirm <package-digest>` performs a read-only check of the original launch record and previously inspected generation. It requires an inactive/failed/absent unit with no main PID, no surviving recorded host or guest generation, no process in that control group (including descendant groups), and no listener on either canary port. The original protected services and every other VM present during collection must remain unchanged. Missing or uncertain observations refuse; stopping a process alone is not evidence of successful recovery.

The command checks retained `state/state.bin` as a private, canonical, bounded, single-link regular file, reads it without following a symlink, checks file identity and timestamps before/after, and repeats the metadata/hash check after process observation. Only ciphertext hash, size and file metadata leave the reader; the buffer is zeroed. These checks show local retention during the observation. They cannot prove successful unseal or detect a malicious host supplying an older valid blob. Incomplete logs remain labelled open; failed logs refuse verification.

Runtime inspection now identifies the new custodian by its own control group rather than rejecting every later VM. This allows the dedicated recipient to run during the secret matrix while requiring it to survive the complete inspection. The generic O.stopped, O.timeout and O.restart journal paths still refuse: actual recipient refusal/release evidence and explicit recovery orchestration remain necessary. No production outage or recovery test was executed by this change.
