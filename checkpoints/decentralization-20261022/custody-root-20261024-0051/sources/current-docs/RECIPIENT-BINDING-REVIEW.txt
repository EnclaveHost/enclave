ANSWER
The r2 (custody v2) release to an SNP app guest is gated by a DIRECT QUOTE at every custodian. The recipient encryption key,
the deployment, the policy/secret revisions, the committee/epoch, every custodian challenge, the runtime and the transport key
are hashed into one 32-byte binding. That binding must appear as report_data[0:32] of a VCEK-signed SEV-SNP report:
  - for an owner-admitted measurement;
  - with report_data[32:64] = the owner's appId;
  - with HOST_DATA = the deployment id.
The registry proofKey is NOT an input anywhere in this path.

A host operator or non-TEE control CANNOT forge a release by registering an arbitrary proofKey:
  - custody/v2/custodian.mjs never reads it; the only mention in custody/ is the registry ABI tuple at chain.mjs:71.
  - The operator's own key only AUTHORIZES (step 7). It can withhold a release, never make one.
The "control proofKey is in-enclave but not SNP-bound in the public verifier" limitation therefore does not weaken custody
release. It concerns checkpoint/metering trust and what a browser is shown.

THREE TRUST PATHS, distinguished
  1. DIRECT QUOTE GATE: custody v2, above. Confidentiality of the owner's secret values rests on SNP hardware evidence for
     owner-admitted images, checked independently by each custodian. Nothing the relay, operator or registry proofKey says can
     substitute for it.
  2. TICKET CHAIN: relay release. provision.go:101-113 binds a relay ticket + seal key into report_data. The relay (platform,
     non-TEE) verifies the report and delivers config / relay-held secrets / the custody POINTER (release/release.go:100-108).
     For custody deployments the relay holds no values (Secrets empty). It does choose the pointer; see caveat A.
  3. BROWSER TRUST: verifier/web/snp-app.mjs and relay-routed attestation display. This is what a user is SHOWN. It is not an
     input to release authorization.

BLOCKERS / CAVEATS for an honest "attestation-gated canary release" claim
  A. INTEGRITY, not confidentiality: the guest does not chain-verify the custody pointer.
     - front/custody.go:116-134 builds the committee (machine encKeys, endpoints, commitments, threshold, bundle) from the
       relay-delivered pointer. No quorum or chain read appears in front/custody.go or custody/v2client.go for the SNP path.
     - So a malicious relay cannot obtain the REAL values (custodians gate them as in path 1, and they only seal to a bound
       recipient key).
     - It COULD point the guest at a fabricated committee and bundle, plus a matching config. The app would then run with
       attacker-chosen "secrets" and config. The config check (custody.go:283-285) compares relay config with a relay-pointed
       bundle.
     - Claim wording should say "values released only to attested owner-admitted guests". Not "the guest provably received
       the owner's committed values" unless the pointer is verified against chain.
  B. Out of this bounded scope, and an assumption the claim depends on: that the committee's custodian machines (their encKeys
     in the chain committee) are themselves attested SNP custodians. That is admission/governance, not the release path.
  C. The gate is exactly as strong as the owner's on-chain rules (measurement/runtime pairs, appId, minTcb, vmpl 0..3). A
     permissive rule (e.g. an image that serves arbitrary report_data, or vmpl > 0) weakens it by the owner's own choice.
     The canary's rules should be stated: vmpl 0, the exact canary image, appId.
  D. Availability, not safety: the host (operator key, lease, relay ticket/pointer, guestd) can deny or stall any release.

No blocker found to the claim "an r2 release reaches only an SEV-SNP guest running an owner-admitted image, verified by each
custodian from AMD-rooted evidence binding the recipient key; registering a proofKey or holding the operator key cannot
forge one". Caveat A must be stated, or closed by a pointer check, before claiming value INTEGRITY.
