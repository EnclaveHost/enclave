# Native desktop startup identity and private networking

The V8 native desktop uses its own approved release for planning, certificates,
privacy enrollment and owner-secret delivery. A GPU allocation does not select
the legacy inference runtime. These checks are source integration; they do not
admit a new image or establish hardware protection by themselves.

The node loads `ENCLAVE_DESKTOP_RELEASE_FILE` only with its exact
`ENCLAVE_DESKTOP_RELEASE_SHA256`. The relay and privacy agent independently
require the matching `policy.desktop` release and one image entry with all
native desktop, protected-port, configuration and secret capabilities. Manager
health and inventory cannot supply those approvals.

During enrollment, the host planner resolves the current public configuration
and catalog version. The controller bytes are bounded and rehashed even if
already cached. The privacy enrollment code derives the V8 record and AppID
again using its own policy. It compares the manager's controller, record, app,
runtime, image, profile, catalog and allocation to those results. An ambiguous,
recovered or launching partition waits; mismatched identity is refused. This
also works for a starting partition, before owner secrets make the app ready.

The enrollment writes `requiresDesktop: true` and `startupEgress: true`. The
startup transport only opens the matching loopback partition relay. The guest
probe verifies fresh, TLS-key-bound evidence against the full Shield policy,
including its security-version floor. HTTP 503 readiness is permitted only for
the configured local startup proof. The automatic native secret courier waits
for explicit startup configuration and a fresh private-route entry. Missing
configuration does not waive that requirement for native apps.

Certificate provisioning uses the planned V8 record and approved desktop
runtime before considering the legacy CPU/inference selector. The manager
view must match the release and the fixed `linux-direct` launch statement.
This node-side monitor-signed consistency check is not hardware attestation;
the relay's independent hardware admission remains required.

## Validation

`test/native-shield-startup.test.mjs` exercises derivation, enrollment, starting
transport, cached-controller verification and secret-courier ordering. Its
public vector is generated by the independent Python V8 reference:

```sh
python3 test/helpers/native-startup-fixture.py > /tmp/native-startup.json
cmp /tmp/native-startup.json test/fixtures/native-startup.json
node --test test/native-shield-startup.test.mjs test/vbs-app-verify.test.mjs test/windows-node-hvcert.test.mjs
node windows/node/deploy-files.mjs
```

The VBS test uses actual TLS and cryptographic verification with explicitly
synthetic TPM roots, signed boot evidence and guest reports. It rejects omitted
native role, a wrong image, nonce/key changes and a security-version floor above
the report. The certificate tests run the CSR/TLS installation flow and reject
mismatched native release fields. These fixtures do not qualify physical
hardware or authorize real owner secrets.

## Release gates still open

The candidate NucBox report's guest SVN 0 differs from the recipe's SVN 13.
Resolve the producer/report identity and verify the real hardware chain; do not
lower the admission floor. The combined graphics platform now has a reproducible
initrd/IGVM and independently validated image mapping. Exercise enrollment,
certificate issuance, sealed secret delivery, masked GPU operations and Moonlight
on the admitted hardware image before publication. One earlier local native
startup hit the supervisor deadline; its cause remains unresolved.
The existing graphics driver supports OpenGL/Vulkan through Mesa with trusted
CPU rendering and a bounded masked integer-affine compute path. General GPU
rendering, gaming performance and API conformance are not established by these
startup tests.

## Combined graphics platform probe

The guest-only `TestNativeGuestKVM` accepts `native.graphics.probe=1` in its
explicit disposable test boot. After the real native desktop reaches readiness,
it locates the unique UID 1000 Fluxbox process in the domain cgroup. A separate
static test helper joins that process's namespaces, forks into its PID namespace,
uses its root and fixed desktop environment, closes inherited descriptors and
applies the actual desktop role policy. The helper is placed in the same cgroup.
It is never added to the production platform archive.

`test/fixtures/native-graphics-role.c` is compiled with the app repository's
`kvm-box/guest/native` include directory; its Python companion is installed only
in the distinct fixture archive as `/probe-native-graphics.py`. The Go test
binary and helper use the same current platform sources as the production
build. The fixture boot still invokes the production verity storage helper;
it does not edit or bypass the production init's vTPM requirement.

The graphics probe runs standard `vulkaninfo --summary` and `glxinfo -B`, verifies
the exact Mesa library hashes, launches `vkcube` and `glxgears` on Xorg `:0`, and
checks their mapped libraries. It identifies the newly managed application
window through `_NET_CLIENT_LIST`, then checks two changing depth-24 frames.
Unmapped windows, Fluxbox decorations and ambiguous application windows cannot
satisfy the check. Each program must change over 1,000 of 43,200 sampled pixels.
The probe also verifies UID, zero capability sets, seccomp and absent physical
GPU nodes. Run it both before normal stop and before worker revocation, and
retain the monitor's process/mount/cgroup cleanup result.

The default probe exercises trusted CPU graphics through the installed standard
APIs and performs zero masked GPU operations. The lifecycle client remains a privileged fixture;
the Wasm controller stays blocked on sealed owner provisioning. It therefore
does not prove real owner authorization, hardware admission or final publication.

Adding `native.graphics.masked=1` runs the bounded affine compute and integrity
case through the real native monitor, guest worker broker and host
`serveDesktopWorker` transport. The distinct fixture archive must additionally
contain the six pinned public affine qualification assets under
`/probe-graphics-assets/`: `prepass`, `prepass-gl`, `linear-prepass.comp.spv`,
`prepass.vert.spv`, `prepass.frag.spv` and `prepass-gl.comp`. The helper copies
these root-owned read-only files into a fresh fixed temporary directory before
dropping to the desktop role. They are never installed in the production image.

The host fixture authenticates the disposable vsock carrier with a per-run
credential, binds it to the exact application/profile/allocation and relays
only to the pinned dedicated GPU worker. After sixteen successful exchanges,
its test-only proxy flips one byte of an actual seventeenth GEMM reply. It must
record exactly seventeen data streams, one mutation and no further GPU stream
for either retry; it logs counts and identities, never protocol bodies or
bridge credentials. This carrier is a Linux test adapter, not the physical
Windows VmId-bound bridge.

The two standard API programs each check 2,048 computed values and buffer guards.
Together they must report sixteen verified offloads and 131,072 MACs; the Vulkan
triangle must match the reference frame hash. The corrupted OpenGL call must
lose its context and skip readback. OpenGL and Vulkan retries must fail without
new GPU work; Vulkan must preserve output and skip the later draw. Normal stop
and worker revocation still require full domain/cgroup cleanup. These tests
establish composition with the actual native platform, not general GPU rendering,
performance, conformance or production authorization.
