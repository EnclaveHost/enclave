# Native desktop startup identity and private networking

The V8 native desktop uses its own approved release for planning, certificates,
privacy enrollment and owner-secret delivery. A GPU allocation does not select
the legacy inference runtime. These checks are source integration; they do not
admit a new image or establish hardware protection by themselves.

The node loads `ENCLAVE_DESKTOP_RELEASE_FILE` only with its exact
`ENCLAVE_DESKTOP_RELEASE_SHA256`. The relay and privacy agent independently
require the matching `policy.desktop` release and one image entry with all
native desktop, protected-port, configuration and secret capabilities. Manager
health and inventory cannot supply those approvals.

During enrollment, the host planner resolves the current public configuration
and catalog version. The controller bytes are bounded and rehashed even if
already cached. The privacy enrollment code derives the V8 record and AppID
again using its own policy. It compares the manager's controller, record, app,
runtime, image, profile, catalog and allocation to those results. An ambiguous,
recovered or launching partition waits; mismatched identity is refused. This
also works for a starting partition, before owner secrets make the app ready.

The enrollment writes `requiresDesktop: true` and `startupEgress: true`. The
startup transport only opens the matching loopback partition relay. The guest
probe verifies fresh, TLS-key-bound evidence against the full Shield policy,
including its security-version floor. HTTP 503 readiness is permitted only for
the configured local startup proof. The automatic native secret courier waits
for explicit startup configuration and a fresh private-route entry. Missing
configuration does not waive that requirement for native apps.

Certificate provisioning uses the planned V8 record and approved desktop
runtime before considering the legacy CPU/inference selector. The manager
view must match the release and the fixed `linux-direct` launch statement.
This node-side monitor-signed consistency check is not hardware attestation;
the relay's independent hardware admission remains required.

## Validation

`test/native-shield-startup.test.mjs` exercises derivation, enrollment, starting
transport, cached-controller verification and secret-courier ordering. Its
public vector is generated by the independent Python V8 reference:

```sh
python3 test/helpers/native-startup-fixture.py > /tmp/native-startup.json
cmp /tmp/native-startup.json test/fixtures/native-startup.json
node --test test/native-shield-startup.test.mjs test/vbs-app-verify.test.mjs test/windows-node-hvcert.test.mjs
node windows/node/deploy-files.mjs
```

The VBS test uses actual TLS and cryptographic verification with explicitly
synthetic TPM roots, signed boot evidence and guest reports. It rejects omitted
native role, a wrong image, nonce/key changes and a security-version floor above
the report. The certificate tests run the CSR/TLS installation flow and reject
mismatched native release fields. These fixtures do not qualify physical
hardware or authorize real owner secrets.

## Release gates still open

The matched NucBox diagnostic established SHA384/P384 identity signing and
authenticated guest SVN 13. The final graphics candidate is still unsigned:
use an explicitly authorized release key, pin its identity, and obtain fresh
evidence from the final signed image without lowering the admission floor.
The signing tool and its exact invocation are documented in
[`tools/vbs-image-sign/README.md`](../../tools/vbs-image-sign/README.md).
The combined graphics platform now has a reproducible
initrd/IGVM and independently validated image mapping. Exercise enrollment,
certificate issuance, sealed secret delivery, masked GPU operations and Moonlight
on the admitted hardware image before publication. One earlier local native
startup hit the supervisor deadline; its cause remains unresolved.
The existing graphics driver supports OpenGL/Vulkan through Mesa with trusted
CPU rendering and a bounded masked integer-affine compute path. General GPU
rendering, gaming performance and API conformance are not established by these
startup tests.

### Image release authority

Native desktop admission now requires `identity` on the same `policy.images`
entry that pins its runtime, launch measurement and desktop capabilities:

```json
"identity": {
  "signer": "<64 lowercase hex characters: SHA256 of the 104-byte CNG public blob>",
  "productId": 1818455653,
  "moduleId": 1734437220
}
```

Those IDs illustrate the diagnostic identity; they do not authorize a production
release. Choose and pin the release authority independently of the guest report.
An all-zero signer is refused. IDs must be unsigned 32-bit integers. A valid
IDKS signature and high SVN under a different release signer cannot satisfy the
pin. Neither can a signer pinned for another measurement. Existing measurement,
runtime, platform, nonce and TLS-key checks remain required.

The shared report verifier accepts `imageIdentities`, a bounded list of
`{ measurement, identity }` records. The relay derives these from its selected
image candidates, and the fresh-report endpoint carries the same records to the
browser. The browser applies the shared check and shows the pinned authority.
The DNS responder also checks the pins before authorizing certificate challenges.
Legacy image sets may omit identity pins; native desktop candidates cannot.
Mixed pinned/unpinned candidate sets are refused rather than treating missing
identities as wildcards. Malformed, empty or null explicit lists are refused.

Tests cover authentic synthetic reports with different signer/product/module,
crossed measurement/authority pairs, high SVN, actual TLS startup probes, DNS
authorization, fresh-report forwarding, and Node/browser/bundled-browser parity.
These changes only implement policy enforcement; they do not install a release
key, change a live policy, or approve the diagnostic key for production.

### Signing the separate image

`enclave-vbs-image-sign` now reads the explicit P384 release key through stdin,
checks its independently supplied CNG public-key fingerprint, and signs only an
input whose artifact SHA256 matches the supplied pin. It derives the launch
measurement itself, refuses existing signatures and unsupported image profiles,
and verifies every original parsed object plus the launch digest after signing.
Output files are created exclusively in a private staging directory; the public
manifest is written last. After syncing, the complete directory is published by
Linux rename-without-replacement, followed by syncing the parent. Its `identity` object has exactly the three fields admission needs,
with `guestSvn` recorded separately.

Ten Rust tests cover atomic output publication, format and cryptographic refusals, including duplicate
identities, multiple platforms and CRC-correct changes to signed fields or pages.
The CLI qualification signs the actual graphics candidate with a disposable
in-memory key, checks it with an independent crypto implementation, confirms
repeat signing is byte-identical, and exercises 36 input/pin/output refusals and
positive checks. It deletes its temporary images and never persists the key.
The tool also accepts the earlier hardware-accepted SHA384 diagnostic artifact
and refuses the three artifacts rejected by hardware (SHA256, changed signature,
and changed SVN). These are local checks against existing artifacts, not a new
hardware admission. The final authorized release key and fresh image acceptance
remain separate steps.

## Combined graphics platform probe

The guest-only `TestNativeGuestKVM` accepts `native.graphics.probe=1` in its
explicit disposable test boot. After the real native desktop reaches readiness,
it locates the unique UID 1000 Fluxbox process in the domain cgroup. A separate
static test helper joins that process's namespaces, forks into its PID namespace,
uses its root and fixed desktop environment, closes inherited descriptors and
applies the actual desktop role policy. The helper is placed in the same cgroup.
It is never added to the production platform archive.

`test/fixtures/native-graphics-role.c` is compiled with the app repository's
`kvm-box/guest/native` include directory; its Python companion is installed only
in the distinct fixture archive as `/probe-native-graphics.py`. The Go test
binary and helper use the same current platform sources as the production
build. The fixture boot still invokes the production verity storage helper;
it does not edit or bypass the production init's vTPM requirement.

The graphics probe runs standard `vulkaninfo --summary` and `glxinfo -B`, verifies
the exact Mesa library hashes, launches `vkcube` and `glxgears` on Xorg `:0`, and
checks their mapped libraries. It identifies the newly managed application
window through `_NET_CLIENT_LIST`, then checks two changing depth-24 frames.
Unmapped windows, Fluxbox decorations and ambiguous application windows cannot
satisfy the check. Each program must change over 1,000 of 43,200 sampled pixels.
The probe also verifies UID, zero capability sets, seccomp and absent physical
GPU nodes. Run it both before normal stop and before worker revocation, and
retain the monitor's process/mount/cgroup cleanup result.

The default probe exercises trusted CPU graphics through the installed standard
APIs and performs zero masked GPU operations. The lifecycle client remains a privileged fixture;
the Wasm controller stays blocked on sealed owner provisioning. It therefore
does not prove real owner authorization, hardware admission or final publication.

For startup diagnosis, the disposable test boot can add `native.startup.probe=1`.
It records elapsed readiness time, fixed per-process CPU/I/O accounting and
cgroup pressure counters, including a final snapshot on failure. It does not
read process memory, command lines, environment, descriptor targets or service
logs. This flag is handled only in the test binary and adds no production
logging or readiness bypass. The fixture waits up to 125 seconds for the
supervisor's bounded 120-second startup; every production readiness check still
has to pass.

A controlled run limiting only the disposable QEMU model device to 32 MiB/s
failed with the old 55/60-second deadlines, while model verification was still
in progress. With 115/120-second deadlines, the same limit reached readiness
in 80 seconds, drew changing OpenGL and Vulkan frames, and removed the domain
and cgroup on stop. Only nsinit and supervisor changed in the root filesystem;
26,029 other paths, including the graphics libraries, were identical. Nine
supervisor checks also cover the actual two-minute deadline and stop during
startup. The evidence is `native-graphics-startup-v1`; it does not establish
the cause of the original uninstrumented timeout or general startup reliability.

Adding `native.graphics.masked=1` runs the bounded affine compute and integrity
case through the real native monitor, guest worker broker and host
`serveDesktopWorker` transport. The distinct fixture archive must additionally
contain the six pinned public affine qualification assets under
`/probe-graphics-assets/`: `prepass`, `prepass-gl`, `linear-prepass.comp.spv`,
`prepass.vert.spv`, `prepass.frag.spv` and `prepass-gl.comp`. The helper copies
these root-owned read-only files into a fresh fixed temporary directory before
dropping to the desktop role. They are never installed in the production image.

The host fixture authenticates the disposable vsock carrier with a per-run
credential, binds it to the exact application/profile/allocation and relays
only to the pinned dedicated GPU worker. After sixteen successful exchanges,
its test-only proxy flips one byte of an actual seventeenth GEMM reply. It must
record exactly seventeen data streams, one mutation and no further GPU stream
for either retry; it logs counts and identities, never protocol bodies or
bridge credentials. This carrier is a Linux test adapter, not the physical
Windows VmId-bound bridge.

The two standard API programs each check 2,048 computed values and buffer guards.
Together they must report sixteen verified offloads and 131,072 MACs; the Vulkan
triangle must match the reference frame hash. The corrupted OpenGL call must
lose its context and skip readback. OpenGL and Vulkan retries must fail without
new GPU work; Vulkan must preserve output and skip the later draw. Normal stop
and worker revocation still require full domain/cgroup cleanup. These tests
establish composition with the actual native platform, not general GPU rendering,
performance, conformance or production authorization.

## Hardware version diagnostic, 2026-10-25

A new verifier-generated TPM challenge on NucBox passed all 31 production host
evidence checks, including the pinned AMD fTPM root, credential activation,
quote/PCR replay, Secure Boot, VBS/HVCI policy and transport-key possession.
The host verifier still reports `hostExcluded: false` and the omission
`platform-firmware-unpinned`. This host evidence grants no desktop admission.
The diagnostic used a separate ephemeral AIK and transport key, with no node
identity key, wallet, owner provisioning or live policy changes.

Both archived reports from the earlier `9c868a4f` kernel probe verify under that
boot's authenticated IDKS. Their signed guest SVN is actually 0; signer,
product and module fields are also zero. With the unchanged floor of 13, each
report passes envelope, VTL, image, recorded-binding and signature checks but
fails SVN. Editing only the SVN to 13 makes the signature fail. These are
historical reports with guest-generated bindings, so this establishes neither
fresh guest authorization nor acceptance of the final graphics image.

The image generator writes the recipe's SVN into companion endorsements without
adding a VBS measurement/signature directive to the IGVM. The locally retained
Microsoft release-2511 `openhcl-cvm.bin` also contains no such directive. Its
absence is consistent with the zero identity fields, but does not by itself
prove how this Windows loader handles signed directives.

A single, separately marked signing experiment preserved every parsed boot
object and the launch digest, then added an experimental VBS identity directive.
Its 60-byte signed-data layout followed OpenVMM's `measurement_diag.rs`; its
P-384 CNG key/signature encoding and SVN tamper rejection verified independently
with Windows CNG. Hyper-V nevertheless refused to start that diagnostic image
before the guest booted. The available VMMS/Worker events only report generic
start failure. **This is not an implemented or accepted VBS signing format.**
Do not reuse the experimental image as a release, lower the SVN floor, or treat
a disposable self-generated signing key as release authority.

The exact probe VM was removed and its unchanged per-run guest state archived
with a matching hash. Before/after inventories retain the same four running
VMs, the same host boot and unchanged Secure Boot/VBS state. The separate
`native-vbs-svn-v1` evidence bundle records the successful host checks, rejected
guest admission, failed signing experiment and cleanup. Next work must establish
the loader's supported signed-identity contract, then repeat fresh guest and
full application admission against the final graphics image.

### Signed identity follow-up, 2026-10-25

The subsequent controlled experiment resolves the signing-hash issue for the
tested NucBox Windows 11 build 26200. Parsing and serializing the unsigned
`9c868a4f` image without adding a directive reproduces its bytes exactly, and
that image boots again on the same host boot. Its two new reports still have
authentic signatures and SVN 0. Direct `Msvm_ComputerSystem.RequestStateChange`
and `Msvm_ConcreteJob.GetErrorEx` expose only a generic failure for the earlier
signed candidate; that error alone does not identify the cause.

A matched pair uses the same disposable P-384 key, 60-byte identity payload,
launch digest and all other header fields. The SHA-256 signature refuses to
boot; the SHA-384 signature boots and passes the kernel/device probe. Both
signatures independently verify with Windows CNG under their intended hash,
and fail under the other hash. The accepted image's two reports verify under
the same-boot TPM-authenticated IDKS with the unchanged minimum SVN 13. They
contain SVN 13, the chosen product/module IDs and a signer equal to SHA-256 of
the 104-byte CNG public-key blob. Flipping a signature byte, or changing SVN
13 to 14 without re-signing, each prevents boot.

The observed encoding is:

- One VBS `0x311` directive with the original compatibility mask and version 1.
- Signed bytes: seven little-endian u32 fields (version, product, module, SVN,
  policy flags, boot-digest algorithm 1, signing algorithm 1), then the original
  32-byte SHA-256 launch digest: 60 bytes total.
- ECDSA P-384 over SHA-384 of those bytes. Store fixed-width big-endian r and s,
  48 bytes each, followed by zero padding to the 256-byte signature field.
- CNG `BCRYPT_ECDSA_PUBLIC_P384_MAGIC` (`ECS3`), key length 48, and big-endian
  X/Y coordinates: 104 bytes total, zero-padded to the 512-byte public-key field.
  Zero-pad the 32-byte boot digest to its 64-byte IGVM field.

This is measured compatibility evidence for that host build, not a universal
published loader specification. The reports use guest-generated bindings;
the prior same-boot host TPM transcript was replayed, not freshly challenged
for these runs. The private signing key existed only in the generator process
and was not persisted. No diagnostic key is release authority. Production work
must pin an authorized signer/product/module, obtain a fresh verifier challenge,
and qualify the exact final graphics image and owner/controller path. A high
SVN signed by an arbitrary new key must not establish release authority.

All six exact diagnostic VMs were removed and their state archived with matching
hashes. The original four running VMs, host boot and security configuration are
unchanged. `native-vbs-identity-v2` contains the public inputs, reports, matched
controls, CNG checks, generic job errors, scoped Claude review and cleanup
evidence. The earlier SHA-256 experiment remains rejected and is not a release.

## Installed-agent startup bridge

`network/native-startup-overlay.mjs` can be bundled separately for an installed
privacy agent whose legacy network and lease modules must remain byte-identical.
The native probe keeps ingress SNI and accepts HTTP 503 only after verifying the
pinned transport key and explicit configured-secret startup expectation.
The native startup forwarder uses the full release identity in
`startingShieldTransport`, current admission and its unexpired verified proof.
It rechecks authorization after connecting, every 500 ms while forwarding, and
closes the stream at the admitting proof's expiry. Any error closes both sockets.
Expected identity is compared by a canonical snapshot rather than object identity.
Ready guests and legacy apps retain their existing manager splice.

The bridge forwards encrypted TLS and cannot inspect HTTP paths. The measured
front therefore retains responsibility for endpoint authorization: sealed-secret
POST requires the pinned relay signature, deployment/nonce binding, and a fresh
challenge; certificate installation checks its authorized name, matching key and
chain. The application remains behind the secret-aware launcher, so its declared
ports are unavailable before delivery. Public attestation/readiness metadata is
intentionally reachable before readiness. This is not client authentication or
a change to the T0-hv host trust boundary.

The compatibility patch must verify the exact installed baseline and match its
three call sites once each. Its `open` must be `startingShieldTransport`, its
`authorize` the live admission reader, and its proof the stored verified proof.
Do not replace an installed bundle with a full rebuild from a different source
snapshot. Test the built sidecar as well as its source before activation.
