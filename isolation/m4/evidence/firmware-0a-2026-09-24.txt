Step 0a: a firmware that VERIFIES the SEV kernel hash table, 2026-09-24, warden-host

THE FINDING THIS ANSWERS. kernel-hashes=on makes QEMU write sha256(kernel), sha256(initrd) and sha256(cmdline)
into a page the launch digest commits to. Whether anything COMPARES the served bytes against that table is a
property of the FIRMWARE. /usr/share/edk2-ovmf/x64/OVMF.4m.fd is OvmfPkgX64, which links BlobVerifierLibNull and
never compares. So "the app is in the measured image" was a statement about hashes on every kernel-hashes path in
this repository - M1, M2 and M4a.

BUILD DEVIATIONS, both in the GRUB image the AmdSev prebuild embeds, because Arch's GRUB ships neither module:
  linuxefi   dropped: a Fedora/RHEL patch, merged upstream into the "linux" module, which remains in the list
  sevsecret  dropped: reads an injected SEV secret to unlock an encrypted disk
Both belong to the AmdSev encrypted-disk-with-secret-injection flow, not to the QEMU -kernel path this project
boots, and BlobVerifierLibSevHashes is untouched by either. THIS FIRMWARE IS THEREFORE NOT SUITABLE FOR THAT
OTHER FLOW.

WHAT THIS RUN SHOWS (isolation/m2/verify-firmware.sh, workdir /home/steven/enclave-bench/fw0a-001446)
  1 control, kernel-hashes=on   the guest BOOTS      PASS
  2 kernel-hashes=off, no table the firmware REFUSES PASS
The same image on the distro firmware BOOTS in case 2 (~/enclave-bench/f0-235238), so this is a behavioural
difference between the firmwares and not a property of the image.

WHAT IT DOES NOT SHOW, and this matters more than the two passes: that a SUBSTITUTED initrd is refused. Cases 1
and 2 show the firmware checks for a table's PRESENCE, not that it compares the bytes. The substitution needs a
QEMU that hashes one file while serving another; that is the review lane's test-only build
(parallel-vmsa-qemu-hashtest, branch test/hash-override) and its fixture, run against this firmware, is the
acceptance for step 0a. A DEBUG build of the same firmware is being produced so the refusals carry the verifier's
own diagnostic instead of being silent.

NOT YET DONE, and required before any suite claims this: m1/domain.env still names the distro firmware. Moving a
SUITE to this one means changing domain.env, because build-domain.sh predicts with domain.env's OVMF while
OVMF_OVERRIDE changes only the launch - predicting against one firmware and launching another would fail check 1
for a reason unrelated to the property.

THE T0 TIER LAUNCHES ON THE DISTRO FIRMWARE, deliberately. A plain non-SNP guest has no SEV and therefore no
kernel hash table, and an AmdSevX64 build meets that by refusing to load the kernel and falling through to its
boot manager - measured here first as a hang: the T0 guest printed "Failed to mount root securely" and "Failed to
find any grub configuration on the encrypted volume" (the missing sevsecret module again) and the suite waited for
a domain that would never serve. T0 is the explicitly untrusted parity tier and no security claim rests on its
firmware, so run-domain.sh picks by mode: the distro firmware for plain, the verifying one for every SNP launch.
Checks 7, 7b and 7c - tier parity, "T0 says it is not attested", and T0 being unable to tell a host in the middle
apart - all pass with that split.

WHAT THE SUITE PASSING DOES NOT ADD. It shows nothing about hash enforcement on its own: the enforcement evidence
is the review lane's substitution fixture against this firmware, and these 24 checks only show that moving to it
broke nothing. A green suite on a verifying firmware is not evidence that the firmware verifies.
