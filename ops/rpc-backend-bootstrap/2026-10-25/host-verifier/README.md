# Host-local verifier package — staged, not running

The host-service runner and privacy-agent policy gate need a verifier that does not depend on the public proof route they admit. This package uses the existing reviewed runtime from control commit `9fa02e1bc6b2179e3a0e1de9d5e98dc16f579b4e` (runtime source `ec56a70f1`), the three previously pinned native binaries, and only the host-local Base backend as its untrusted proof source. It serves the local verifier protocol on loopback port 28590.

`build.mjs CLEAN_SOURCE NEW_OUTPUT_DIR` refuses dirty tracked source and existing output. It builds one standalone Node 20 ESM entry, rejects unresolved non-builtin imports, and records every bundled input hash. Two builds produced the identical 129250-byte bundle `7aa504eb639b9e1c6eb18f4775f13927cf6eceec83e42b5edd92dbac1066f124` and identical manifests. Native binaries remain separately pinned; they are not compiled by this recipe. The listener is release-profile; Helios and witness-check remain the reviewed debug builds.

`stage_local.py` is the exact desktop-specific staging adapter, using this task's fixed work layout. It verifies binary and bundle hashes before creating a new directory, refuses replacement, copies and rechecks the binaries, and writes a public configuration. It does not start or enable a service, create a readiness marker, read any key or contact a chain. The actual stage is `/home/steven/enclave-prod/rpc-host-verifier-7aa504eb`; state will live in `/home/steven/.local/state/enclave-rpc-host-verifier`. There is no witness cache or Sia archive configured. Runtime binaries and small bounded runtime state are not chain data caches.

The bundled CLI `check` passed against the actual staged files and system flock; this confirms config/pins/tools, **not chain readiness or runtime operation**. `systemd-analyze --user verify` accepted the rendered unit. Build peak was 101 MiB under the shared guard. No runtime memory benchmark is claimed by that preflight.

The unit template is not installed or enabled. It caps the verifier at 1536 MiB with no swap and keeps every descendant in its service cgroup. The startup preflight reserves that allocation in addition to the 16 GiB host memory floor. The state directory must exist with mode 0700 before activation; its `activation-reviewed.json` condition is deliberately absent. Create that record only after reviewed chain acceptance and the canary plan, naming the acceptance evidence and intended scope; it is an operator release latch, not a cryptographic readiness proof. StateDir kernel locking, pinned copies and fresh-head refusal are enforced by the runtime itself. A start must still be verified before changing any consumer.

Required before rollout: Ethereum EL/CL and historical blob/receipt coverage; Base advancing safe and finalized heads; positive and failure-path checks through this bundle; RPC route and administrative-policy canaries; the desktop's pending shutdown-timeout fix. These are not established by this package. Keep previous consumer configs/images for rollback. Stopping this user unit removes the verifier and its children; do not remove the chain VM disks or signed transaction journals.

Trust: the verifier checks proofs against sequencer-signed **unsafe** heads. It does not derive L1 finality; that remains a separate backend acceptance check. Its proof source is untrusted for correctness but required for availability. One host/backend is a single-site bootstrap. Do not tunnel this loopback API to an exit and describe the exit as locally verifying proofs; remote authority requires a separately reviewed trust model. No existing service, administrator control, app, or consumer config changed.
