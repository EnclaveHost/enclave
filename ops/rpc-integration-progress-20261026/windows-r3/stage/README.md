## Bundle closure (`jobs/bundle-closure.mjs`, called by the r3 job)

- **The helper:** for `network/host-admission-node.mjs → windows/node/host-admission.bundle.mjs` and
  `network/metal-host-policy.mjs → metal/guest/host-policy.bundle.mjs`, it uses **the exact esbuild options of
  `build-host-admission.mjs`** plus `metafile`, which does not change the output bytes. It records the committed
  sha256, the generated sha256, stale or current, and **every input file's sha256**. It writes nothing.
- **The job, step by step:**
  1. **Two fresh clones:** an UNPATCHED baseline at `aebf4c932` (files checked against `BASE-aebf4c932.sha256`) and the
     candidate (r3 patch, `CANDIDATE.sha256`).
  2. **Lease bundles:** both must pass `--check` UNCHANGED in both trees.
  3. **Closure before:** run on the baseline and on the candidate. The actual baseline staleness is printed and kept in
     `bundle-closure-baseline.json`, the published evidence.
  4. **Rebuild:** the candidate's host-admission pair is rebuilt by the repo's own `build-host-admission.mjs` from its
     exact source, then `--check`ed.
  5. **Closure after:** run on the candidate.
  6. **Required, or exit 20 (setup, never a verdict):**
     - both rebuilt files are current;
     - the rebuilt bytes equal the helper's generated bytes;
     - baseline and candidate input sets and generated bytes are identical, or else every differing input is a patched
       file.

     The r3 patch is not expected to touch any bundle input: `enclave-network-host.mjs` is not in either bundle, since
     `network/privacy-agent.mjs` imports it from source.
- **The helper is copied into each tree before it runs** (`.r3-bundle-closure.mjs`), so `esbuild` resolves from that
  tree. That is the run 0114 lesson.
- **What this means for the source:** the regenerated `windows/node/host-admission.bundle.mjs` (and the metal
  host-policy bundle, if stale) must be **committed in the source** together with this patch. The job produces and
  hashes them, but never commits them.

## Root item: the network host's contract-wallet owner signatures under the verifier

**The change** (`network/enclave-network-host.mjs`): a new `ownerSignatureReader({pins, leaseReader})`. It returns:
- **pinned:** the quorum reader, unchanged;
- **the agent's `LeaseReader` IS the explicit verifier** (`authority 'verifier'`, built from
  `cfg.chain = {addressBook, authority, verifier}`): that same reader;
- **otherwise:** `undefined`, the legacy multi-client path, unchanged.

**Effect:** `verify = verifyOwnerSignature({clients, reader: ownerSignatureReader(...), …})`. Under the verifier,
ERC-1271 passkey vaults and SessionVaults are checked by `oneClient` at ONE verified block through the verifier's
pinned client. Every `eth_call`/`eth_getCode` is pinned to that block's hash. There are no public clients and no
fallback. EOA owners still recover locally.

**Egress probes, to avoid a functional regression:** `probeEgressUrls([])` throws, and without `rpc` the agent had no
probe origins.
- `chain.mjs` `connectivityProbeUrls()` hands the agent explicit **connectivity-only** probe origins under the
  authority: the node's configured list's origins, or `ENCLAVE_NETWORK_EGRESS_PROBES`.
- They pass through `agent.mjs` → `networkConfig(egressProbeUrls)`, which validates HTTPS without credentials, 8 at
  most.
- They are not a chain authority (`network/egress-probes.mjs`).

**Also carried from r2:**
- startup through `verifierReader` (the same per-read policy);
- the agent's `cfg.chain` follows the explicit authority (public `rpc` removed, mixing refused, invalid gives no RPC);
- admission with `rpc: []` under the verifier;
- every `chain.mjs` read and the operator wallet use the routed authority, with sends gated (own backend only, never
  the verifier);
- `rpcUrls()` is `[]`.

**Unchanged:** heartbeats, signatures, admin controls, legacy behaviour and measured or security gates.
