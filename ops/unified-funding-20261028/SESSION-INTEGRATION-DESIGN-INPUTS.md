# Inputs for the next session integration review

This is a design brief, not a contract or authorization. User explicitly prioritizes full funding release and permits the funded session to sign within actual on-chain authority. Existing $30/zero-spend session and deployments remain untouched.

Confirmed existing SessionVault source hash a447add6f44ca65ecdf19625450623dce5c41270a28f0ab2b3240382d3ceeb1c matches the historical reproducible deployed-source record (23664 bytes, optimizer runs1/viaIR, only912 bytes below EIP170). Live factory/implementation hashes match record. Original factory and later pinned factory both exist in checked-in deployment records; do not replace original address-book entry blindly. Old custody owner resolution and old vault release depend on these identities. No runtime upgrade exists in an immutable clone.

The new DEX adapter consumes a maximum approval, refunds unused USDC to its payer, returns actual debit, credits exact ETH to (deployment, expectedOwner), and enforces immutable route/ownership/delta constraints. Current candidate has no offchain authorization itself: caller=payer. An old P256 session cannot call it. Permissionless deployment itself needs a transaction sender; existing session grants have no deployment action.

Review a successor design with explicit new action bit >=10 (9 retired), new signed authority/version, max gas USDC per operation, max USDC per ETH, max ETH per operation, existing total/period/ops/app/env limits. Preserve unchanged old grants and deployment recovery. Actual amount+explicit capped relay fee must debit once; unused swap input must return to SAME session without incrementing available liability twice. Reserving maximum then refunding unused budget must restore balance/spent/periodSpent/locked exactly while consuming one operation; prechecking max then charging actual after external call must still be nonreentrant and cannot let concurrent signed calls bypass accounting. Prove both budgets and token conservation adversarially.

Current execute fee goes to treasury PaymentRouter, not successful independent submitter. New funding execution needs an explicit signed fee/recipient policy and direct reimbursement mechanism, avoiding accidental fee duplication or front-running theft. No arbitrary target/calldata from a quote. Do not use an old deploy.fund or fee field as swap authority. Native ETH not needed by user once relayer has a genuinely reimbursement-capable signed call; deployment/grant opening still need proven bootstrapping.

Seven recovery app IDs are wallet-owned; two remain owned by old B794 vault. Funding a new-vault-held deployment only is insufficient. Gas funding of old-vault-held apps must preserve deployment/custody ownership and require proven owner/env/app scope (e.g. a pinned legacy factory plus exact vault owner and held environment, or a new explicitly signed exact-target policy). A generic arbitrary contract owner() response is not proof of trusted vault ownership. Migrating ownership can break secrets/reserve keys; do not do so merely to fund gas.

Existing reserve allows owner ETH withdrawal. Closed-loop compute credit cannot feed that freely withdrawable balance without source-aware accounting/refund restrictions or an explicitly reviewed change in rights. Backing of old fundEth accounting-credit payouts must be reconciled; never pretend credit mints ETH. First release slice USDC->ETH can be additive; full unified funding still requires ETH->backed services and restricted credit->gas, planner/dashboard/CLI and canary acceptance.
