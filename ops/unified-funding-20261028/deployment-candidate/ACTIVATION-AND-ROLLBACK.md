# Unified funding: prepared additive deployment and activation

Status: preparation only. The unsigned four-transaction proposal is NOT signable or approved for production. No nonce reserved, signatures obtained, old grants ended, funds moved or services changed. This first release slice enables explicitly granted USDC-to-app-gas funding; it does not complete ETH-backed compute or restricted-credit conversion.

## Reviewed source and unsigned transactions

The proposal reads Base through PublicNode and Blast, requires matching chain/block/runtime/owner/constructor bindings, and requires latest and pending administrator nonces to agree. At block53205633 the observed administrator nonce was1175. Predicted addresses and initcode are provisional; any nonce change invalidates them and requires regeneration/replay. Four transactions deploy the existing-behavior library, gas library, DEX adapter and additive successor factory; the factory creates its implementation internally. All initcode and runtimes fit standard EVM size limits. Constructor bindings preserve original USDC, address book, payment router, key-attestation registry,250USDC vault cap and old factory. Adapter maxEthOut0.001ETH is an immutable outer safety ceiling, not a session spending authorization. Actual session grants must be narrower.

The exact artifact hashes match the reviewed relay-owner-r2 artifact manifest. Original dependencies are only read. No factory/address-book entry is replaced. The staged fork runner impersonates the administrator ONLY on its own loopback Anvil and fabricates test ETH there; it has no wallet key, no public RPC mutation methods and no production signing authority. Fork replay is required to record exact runtime bytes/hashes, sequential constructor success and gas estimates. Do not treat a queued replay as passed.

## Production release sequence

One coordinated submitter. User reviews concrete owner/deployment/new-grant transactions only after the above gates pass. For each deployment, verify exact sender/nonce/calldata/value, canonical nonzero-block receipt, intended contract address and full runtime bytes before the next dependent call. Pending/ambiguous submission is reconciled, never blindly repeated. Store signed transaction hash and durable journal before considering completion.

Activate the new route only after exact runtime/link/constructor pins, fee-policy configuration and the new grant are independently checked. Use the reviewed live feed and L2/L1/operator fee calculation; fee is explicit capped compensation, not exact gas reimbursement. Preserve old routes and owner controls. Run one small production gas-funding canary against the refreshed KVM recovery inventory; verify actual USDC debit, input refund, one capped fee, reserve credit to the correct holder and all budget/period counters. Then refresh prices/reserves again and fund only the still-needed amounts for the remaining apps. Let normal claims resume; verify leases, TLS and application endpoints. Do not call eligibility, pool acceptance or reserve deposits successful app recovery.

## Rollback and incident containment

Disable new funding intake/quotes through the additive feature gate while retaining authenticated owner terminate/revoke/withdraw controls. A routing failure must never lock owners out. Freeze new submissions and preserve durable intent/transaction journals; inspect and reconcile every known or ambiguous transaction before any replacement or resubmission. Never restore a stale journal over newer nonce ownership or remove pending records to make retries pass.

Before owner-grant activation, additive contracts can remain unused and the original relay/config can be restored after reconciling pending sends. After a new grant exists, first revoke/terminate it using the owner's existing or reviewed successor controls and confirm canonical results before refund/withdraw. Restoring the old relay alone does not revoke a new on-chain grant. On-chain swaps and confirmed reserve deposits are not undone by code rollback. Recovery must retain actual credited holder/refund rights; do not withdraw someone else's reserve or treat nonwithdrawable credits as cash. Deployed immutable contracts remain on chain; rollback means disabling use and restoring service configuration, not deleting them.

Keep original factories, address-book entries, custody policies, deployments, apps and controller credentials unchanged. Preserve installed pad-guard files and host memory/admission floors. No RPC VM/GPU experiments are part of this release.
