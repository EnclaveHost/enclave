**Existing routes do not remove this blocker.** [transferDeployment](/home/steven/Documents/Codex/2026-10-23/it/work/wallet-ownership-migration-review-r1-20261029/ledger-rev16d-EnclaveDeployments.sol:958) changes only the record owner, preserving ID and other fields when it succeeds. [Vault release and ownerCall](/home/steven/Documents/Codex/2026-10-23/it/work/wallet-ownership-migration-review-r1-20261029/legacy-sessions-v2-SessionVault.sol:833) still call that guarded entry point. `ownerCall` has no privileged storage access, forbids multicall, and cannot forward ETH. Ledger multicall preserves each inner call's authorization. Admin ownership transfer changes the contract administrator, not deployment ownership.

[settle/credit](/home/steven/Documents/Codex/2026-10-23/it/work/wallet-ownership-migration-review-r1-20261029/ledger-rev16d-EnclaveDeployments.sol:1884) pays only actually earned/proven time; it cannot lawfully erase outstanding backing to make a transfer pass. Runner `release` clears lease accounting, not owner escrow. [refund](/home/steven/Documents/Codex/2026-10-23/it/work/wallet-ownership-migration-review-r1-20261029/ledger-rev16d-EnclaveDeployments.sol:1899) pays the free portion, retains possible runner liability, **zeros runtime balance and deactivates**. Refunding then re-funding buys runtime again through fee splitting; it is not preservation. `sweepEscrow` requires a drained record and sends residual escrow to payout. None is a migration bypass.

[importDeployments](/home/steven/Documents/Codex/2026-10-23/it/work/wallet-ownership-migration-review-r1-20261029/ledger-rev16d-EnclaveDeployments.sol:1472) rejects an existing ID even before imports seal, and resets runner/lease fields on a successor. [importEarn](/home/steven/Documents/Codex/2026-10-23/it/work/wallet-ownership-migration-review-r1-20261029/ledger-rev16d-EnclaveDeployments.sol:1545) copies the rate only: actual escrow and operator earnings remain on the source. Copying accounting into a new ledger neither moves the backing nor extinguishes old refund/earning rights. Global retirement is unnecessary for this review and is not proposed.

**Old gas ETH is recoverable, but reserve continuity is a separate missing capability.** [budgetKey/deposit/configure/setClaimant/withdraw](/home/steven/Documents/Codex/2026-10-23/it/work/enclave-deployment-lifecycle/contracts/EnclaveLeaseGasReserve.sol:298) key reserves by `(id, owner)`. A direct wallet call through the old vault can withdraw its remaining ETH to the same controlling wallet even after ownership transfer; that is recovery, not loss or new funding authority. Subsequent deposit targets the new current owner. However, `configure` and `setClaimant` cannot copy epoch spending, epoch claim count, last claim time/operator or all historical allowances. A fresh bucket can reset effective budgets/cooldowns. No atomic reserve reassignment/import endpoint exists. The reviewed reserve file still matches its prior source pin; no new runtime verification was performed.

The **smallest missing interfaces**, specified as behavior rather than an unreviewed ABI, are:

1. At the ledger: an actual-owner-authorized **transfer with backed refund rights**, narrowly validating that the destination is the verified controlling wallet (or explicitly consenting beneficiary). It must retain the same ID, balance/spent, fee/cap/config, runner/lease/proof meter, escrow and accrued operator claims; deliberately reassign the right to future owner refunds without a refund, fee split or duplicate claim. Bind the expected source owner and economic/content state so a stale authorization fails. Ordinary `transferDeployment` should retain its existing money-protection gate.
2. At the reserve: a coordinated **owner-bucket reassignment**, moving the remaining ETH once, preserving policy and effective spending/claim/cooldown counters and authorized claimants, consuming the old bucket, rejecting unreviewed destination-bucket collisions, and refusing during an executor begin/finish operation. A stable budget identity with an authenticated owner update is another implementation, not an existing feature. Do not manufacture a fresh budget by resetting counters.

These are missing capabilities in the immutable contracts, **not functions a new front-end/helper can add to the old addresses**. A replacement contract alone cannot write the old ledger or extract its escrow. Full preservation on the current ledger address is therefore unavailable through its published interfaces. A successor/per-app economic migration would need separately designed reconciliation and source-side asset recovery or explicitly funded replacement backing; this review does not claim that path is already available or authorize it. Delegating wallet control while leaving the vault as record owner does not meet the requested ownership migration.

**cab8 differs: its blocker is an owner content-policy decision, not funded escrow.** Under the stated complete-census premise (sole live session env3, no other relevant delegates), the session is already permitted the common production actions before transfer. [Vault dispatch](/home/steven/Documents/Codex/2026-10-23/it/work/wallet-ownership-migration-review-r1-20261029/legacy-sessions-v2-SessionVault.sol:1037) forbids session `setAppRef/setConfig` in production both before and after wallet ownership. There is no new session ability to write those two on-chain fields simply from this move.

There **is** a real change to effective secret-release policy: captured installed [custodyRefusal](/home/steven/Documents/Codex/2026-10-18/wo/work/rpc-production-final-20261025/unified-funding-20261028/wallet-migration-installed-policy-r1/sessions.mjs:1609) refuses unpromoted PROD but passes a plain wallet. Its installed legacy, attested and Shield callers use this check. The owner can authorize that change; the immutable vault does not forbid its owner from releasing an unpromoted record. This is not proof of unchanged policy, and an env3 grant alone is not owner approval of content. The [installed evidence limits](/home/steven/Documents/Codex/2026-10-18/wo/work/rpc-production-final-20261025/unified-funding-20261028/wallet-migration-installed-policy-r1/ROOT-REVIEW.md) remain: captured files tied to service identity, not all loaded host/remote-backend code.

The narrowest honest product path is an explicit owner review of exact current `appRef`, `configCid`, their commitment and the secret-release consequence, followed by the existing Release under fresh pre-sign/post-sign checks and receipt reconciliation. **Release signs deployment/to/nonce/deadline, not content**; an acknowledgement attached only in local UI is not an on-chain content condition. If a cryptographically content-bound owner approval is needed, the already-deployed [Promote](/home/steven/Documents/Codex/2026-10-23/it/work/wallet-ownership-migration-review-r1-20261029/legacy-sessions-v2-SessionVault.sol:789) provides it: name the unchanged exact current ref/config and verified catalog label/publisher, confirm promotion, then Release. Its [library](/home/steven/Documents/Codex/2026-10-23/it/work/wallet-ownership-migration-review-r1-20261029/legacy-sessions-v2-SessionVault.sol:284) avoids setting ref/config when they already match. This introduces an explicit policy authorization, not an operator allowlist or a new protocol prerequisite. No promotion was performed here. `adopt`/`setEnvironment` are not substitutes: actual `_setEnv` clears promotion, despite an older misleading adopt comment.

Remaining content paths must be described accurately. Installed [secret mutation](/home/steven/Documents/Codex/2026-10-18/wo/work/rpc-production-final-20261025/unified-funding-20261028/wallet-migration-installed-policy-r1/secrets.js:163) requires the beneficial owner's wallet signature, not a session key. Reviewed host [restart](/home/steven/Documents/Codex/2026-10-18/wo/work/rpc-production-final-20261025/source/windows/node/host.mjs:663) reloads the recorded deployment; [api.appAccess](/home/steven/Documents/Codex/2026-10-18/wo/work/rpc-production-final-20261025/source/windows/node/host.mjs:3350) forwards authorized requests into the app, whose own mutable endpoints may change runtime state. Thus no demonstrated session path here changes the protected on-chain ref/config, but this is not proof that all runtime content is immutable. Host installation and app-specific mutable/admin endpoints were not captured in the relay evidence. Owner direct operations, previously signed owner operations and any other ledger delegates remain separate writers; recheck the relevant actual census and content before dispatch. Do not invent absence of these paths, or expand this into a blanket unrelated platform approval requirement.
