## Conclusion

The verified deployed ledger has `create`, not `createFor`. A client/relay-only change cannot make the existing immutable session vault create wallet-owned records with its current session authority. A new authenticated executor/vault implementation can use the existing ledger: create an empty record, transfer that same ID to its verified controlling wallet, then fund it with wallet payer attribution, all in one transaction. No replacement ledger is required for this future-create sequence. This is an implementation candidate, not a deployed or tested solution.

“Wallet owned” here means the final committed state. The intermediate Created event still names the executor and must be followed by DeploymentTransferred in the same receipt. If the requirement instead demands that even creation itself have the wallet as creator, the reviewed ledger has no delegated creation interface; that is a different contract/account execution design.

## Smallest complete implementation boundary

1. A new verified session executor/vault version keeps the current signature, replay, expiry, attestation, operation/budget/period/fee checks and catalog-derived publisher-fee validation. `_create` uses the fixed verified controlling wallet, never a caller-supplied destination. Capture one ledger address; create -> transfer -> verify owner -> fundFor(id,fund6,wallet). Any failure reverts the whole transaction. Preserve ordinary fee accounting once, allowance consumption and the returned ID. New IDs remain executor-nonce derived; transfer must not derive a replacement ID or hostname.
2. Explicit owner-approved delegation is needed for later owner-gated operations. Ledger `setDelegate`559–572 covers EVERY wallet deployment, not just the new app. The executor therefore must enforce session app/deployment scope on every operation before invoking the broad ledger delegate. Existing `_dispatch`1005–1076 does not uniformly enforce apps[] on common operations; do not reproduce that gap or grant a new broad delegate silently. Funding is permissionless at the ledger but still requires session budget/scope checks.
3. Decouple authenticated environment/content policy from ledger custody, consistently across executor, relay, host and secrets. Current `_requireHeldEnv`1104 uses held metadata first, otherwise wallet-owned means PROD. I/sessions.mjs:158 and S/windows/node/session-api-auth.mjs:346 instead classify by actual ledger owner; I/sessions.mjs:1609 custodyRefusal lets plain wallets pass without the vault promotion commitment. Simply keeping held[id] after transfer creates disagreement; deleting it loses staging semantics and can remove a production content gate. A wallet-authorized policy binding must preserve environment, exact-content promotion, owner control, revocation and fail-closed reads for all consumers. No automatic promotion on create.
4. Recognize the new verified factory/implementation in SDK/relay/host/secret resolvers; bind grants to its actual chain/vault domain and finite budget. Existing signatures or balances are not automatically portable. CLI/UI must report actual wallet ownership and process the final transfer event correctly. Keep app.publish/catalog ownership separate: existing `_publish`1093 also publishes as the vault and is not fixed by deployment transfer.

The existing create tuple can potentially remain ABI-compatible because the destination is fixed on the executor. The necessary contract deployment plus consumer-policy changes make this larger than a one-line frontend fix. No source-only alteration to already deployed immutable bytecode is available. Tests should cover atomic rollback, owner/ID/event consistency, fee/refund attribution, scoped subsequent operations, environment/content agreement, grant domains and budget continuity before production activation.
