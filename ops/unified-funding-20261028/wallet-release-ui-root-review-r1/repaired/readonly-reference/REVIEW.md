## Smallest existing deployment-transfer path

1. For each actual ledger row owned by a verified SessionVault, establish its controlling `owner()` wallet independently through its known factory/implementation and current identity evidence. Do not infer control from host payout or an unverified arbitrary owner() function. Record the ledger ID, owner, appRef/config/ports/resources/public flag, active state, balance/spent/escrow, runner and lease, and associated reserve/policy/custody identity. Skip rows already owned by the target wallet; preserve prior receipt/nonces to avoid replay.
2. rev16d `transferDeployment` (958–964) requires the actual record owner as msg.sender, destination nonzero, and `ownerEscrow6[id] == 0 || earn.escrow6 == 0`. It changes ONLY d.owner and emits DeploymentTransferred; ID, balance, config, runner/lease and fee snapshots are not modified. A delegate cannot transfer. Root must simulate the exact call against current state.
3. Prefer existing `SessionVault.release(id, ownerWallet, opNonce, signBefore, ownerSig)` (833–844) if its book resolves this exact ledger. It permits the controlling wallet destination, transfers from the vault, then deletes held metadata. The owner can call directly, or sign EIP-712 Release for a relayer. SDK `ownerOperation({op:release,...})` and relay POST /v1/sessions/owner already support it. A live session key cannot substitute for the owner signature.
4. When the vault book points elsewhere, the owner's direct `vault.ownerCall(actualLedger, encode transferDeployment(id, ownerWallet))` (851–863) addresses the exact ledger and clears held metadata for this selector. ownerCall requires msg.sender==vault.owner, is not a signed-session operation, forbids generic multicall, has no value forwarding, and cannot target USDC or the vault. No automatic executor/session authority should be invented.
5. Handle reserve continuity alongside transfer, below, then independently confirm the ownership event and full preserved state at a fresh consistent block, plus app-serving and secret-access behavior. Do not restart or refund an app just because transfer changed its owner. One ledger transaction does not prove the whole migration succeeded.

## Escrow is a genuine blocker, not a UI issue

If both owner-attributed escrow and held runtime escrow are nonzero, transfer reverts `refund first`. rev16d refund (1369 and library 1899 onward) is cancellation: it zeroes balance6, deactivates the app, pays only the refundable portion and retains liability for the lease tail. It is not a harmless precursor to ownership migration. Importing into a replacement ledger also resets lease fields and does not automatically carry earnings/escrow. No no-loss/no-interruption bypass of this gate was found in the existing transfer surface. Root should report exact blocked rows and qualify an explicit migration path instead of blindly refunding, spending down, transferring to another vault, or redeploying under new IDs.

## Gas reserve and funding continuity

The reviewed EnclaveLeaseGasReserve source keys reserve/policy/claimants by keccak256(id, owner). Its admission reads the CURRENT ledger owner. Transferring the app therefore selects a new wallet bucket; old vault ETH, enabled status, caps and claimant permissions do not follow. `withdraw(id,amount,to)` at 349 reads the caller's old bucket without a ledger ownership check, so the controlling wallet can still use old vault.ownerCall(reserve, withdraw(id, exactAmount, wallet)) after transfer. That only recovers the old reserve; it does not enable the new one. New wallet configure (325), setClaimant (341) and deposit (302) must be explicitly qualified. deposit credits current owner; configure/claimant require current owner. No transferReserve method exists in this source. No new deposit/payment is performed here.

Preserve finite remaining balances and compare old/new buckets; avoid duplicate funding, a surprise sponsorship gap or resetting spent caps as if migration grants a new budget. If atomic batching is needed for service continuity, prove the actual wallet's supported execution path and all postconditions first; ownerCall itself is not a batch/value-forwarding mechanism. Root must check the actual reserve deployment/version and any funding-session grants bound to the old owner/domain.

## Secrets, session/API access and serving state

EnclaveSecretVaultV2 beneficialOwnerOf (466–474 in current reviewed source) unwraps a recognized session vault to its wallet. Where the pre-transfer beneficial owner already equals the same target wallet and pinned policy owner, this migration need not change policy ownership or encrypted content. Verify that fact for each actual secrets backend/factory. Do not call claimPolicy speculatively: the claim path destroys the old encrypted bundle and pauses the new policy when beneficial ownership changes.

The relay's custodyRefusal (1172 onward) treats wallet-held rows differently from vault-held environment/promotion records; deleting held is expected, but must not silently loosen approved content or release secret state inconsistent with the intended owner policy. Verify current appRef/config and preserve existing secrets; no secret values need to be read or copied for this review.

Host session authorization `windows/node/session-api-auth.mjs:346–363` changes from vault-held environment policy to wallet-held PROD plus the wallet's explicit ledger delegation. Thus an app can keep running yet its old session lose API authority after transfer. Existing `setDelegate(vault,true)` is wallet authorization, not app ownership. Respect existing scope/environment restrictions; do not silently grant broad rights. Host caches and owner-based views must refresh to actual new ownership. No resident restart is justified by these source findings.

## Catalog-owned apps are separate

Exact catalog `transferApp(appId,to)` (610–624) preserves appId, references, versions, approvals and fee snapshots, changes publisher, and creates the destination slug redirect. It requires the CATALOG ADMIN, not the publisher/vault, and refuses a conflicting destination slug. An ownerCall from the vault is insufficient unless that vault is also the catalog admin. Inventory these separately; confirm actual admin authority. Existing paid deployment fee snapshots remain at their old recipient even after catalog ownership moves. Do not duplicate-publish an app or delete a conflicting lineage to evade this gate.

## Prevent future vault ownership (follow-up after existing migrations)

Actual CLI path: cmdDeploy -> deployViaSession (cli/enclave.mjs:1939,3371) -> SDK Session.call('deploy.create') -> relay /execute (sessions.mjs:764) -> SessionVault.execute/_create (1079) -> SessionVaultLib.create -> ledger.create (625). The ledger assigns d.owner=msg.sender (652), so the vault owns the record; a caller-supplied UI owner label cannot change it. Current browser deploy.js wallet path calls the ledger directly; its credit-vault branch has separate ownership semantics and should not be conflated with a session.

Smallest source-level future SessionVault change to investigate: within authenticated _create, create the empty record, immediately transfer it to the vault's fixed owner BEFORE funding, and fundFor with that wallet as attributed payer. Verify owner postcondition atomically; preserve scopes, spend ceilings, replay protections and refund attribution. New grants/manager calls need compatible explicit delegation and environment/content policy; don't accidentally treat all new wallet-owned staging apps as unrestricted production. Existing immutable clones cannot be patched by changing SDK text or factory configuration, so a new qualified contract path/version is required. The previously requested publish action also currently publishes as the vault, and needs its own wallet-owned publishing design. This is a proposed follow-up, not implemented or deployed.

## Explicit self-hosted USDC funding requirement

Top up must offer **Add runtime (USDC)** for self-hosted apps as well. The authorized USDC must automatically convert to gas as needed; zero host runtime pricing must not hide this funding option or imply no transaction costs. Ownership migration must preserve existing and future authorized USDC/gas budgets and refund attribution. Distinguish old reserve (id,vault) from new reserve (id,wallet), and bind each session/adapter/grant to its real owner/ledger/reserve/controller/scope. An old approval or grant is not automatically authorization to spend through a new target. Maintain one finite budget across migration; moving or recovering existing funds is not a new funding allowance. This review does not implement automatic conversion; UI text alone would not satisfy it.
