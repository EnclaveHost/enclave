## Decision

No qualified zero-interruption enablement exists in this installed interface. Hosting is statically imported and initialized once with the Host instance; there is no trusted hot-load/IPC route to invoke its private give-up method. Editing disk source alone does not change the running instance. A sidecar importing chain would be another signer/nonce queue and is excluded. An inspector/runtime-injection mechanism is excluded. Host caps/pause, placement changes and manufactured app failures are excluded.

Smallest source path: add one targeted local-owner route to existing hosting controls, one public Host release-stopped method, and a narrow optional release guard inside the existing shared chain queue. No new operator, signer, reserve sender, session grant, journal backend or ledger contract.

## Unavoidable disruption and affected scope

Loading edited static modules requires a controlled stop/start of the SAME node-agent role, with old process confirmed gone before the new one can use the signer/journal. No overlap/second signer. There is no proven hot reload in this build.

Unavoidable minimum interruption: node-owned9600 and9610 listeners, relay WebSocket/app-zone connections, in-process proxy streams and renewal/proof/control tasks stop until startup/reconnect/reconciliation succeeds. Every app whose traffic uses this agent proxy can see connection drops, even though only DNS is being released. It is not honest to describe the cutover itself as per-app zero downtime or give an unmeasured duration. Direct VM networking may survive, but that is topology-dependent and requires actual observation. Renewals/proofs are delayed; a long startup can let other leases lapse.

Desired preserved runtime: do not stop the separate isolation manager, router services, Hyper-V guests, network agent or unrelated applications. The isolation-only startup path queries the manager and can adopt matching existing domains. This is conditional, not a universal guarantee: source host1305–1324 deliberately retires/reboots manager-marked recovered VMs. Therefore restarting the manager would expand disruption to VM reboots and must be excluded. Source agent1197 SIGINT kills supervised legacy host/worker children; if LEGACY_ENGINE is actually active, those workloads restart too. Task/job termination may kill additional descendants; current ancestry/job boundaries are not proven by file hashes or listener identity. If they cannot be isolated, the exact affected scope is broader and must be reported before any activation.

A controlled agent-only interruption plus subsequent individual DNS/KVM release is the smallest plausible path. No fully serving-preserving activation has been demonstrated. If the user requires no agent-proxy interruption at all, this installed version cannot meet it under the no-injection/no-second-signer constraints.
