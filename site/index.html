Two questions hide inside "is it isolated": from other apps, and from the machine's owner. Hosts answer them differently, so each listing carries its answer as a badge. These are the levels that exist today and the one that is planned.
confidential · available

The host cannot see in

The machine's operating system and its operator are locked out of the app's memory and traffic, and the processor signs a report you verify before connecting. Where a GPU is inside the boundary, it attests too. This is the hosted fleet and every self-hosted confidential server. Between apps on one such host, separation is a sandbox and a process today; moving it into hardware is in research.

partitioned · available on one host

Apps kept apart; the owner can see in

A Windows PC runs apps inside an enclave its own operating system cannot read, but the person who holds the machine ultimately controls it: no memory encryption, traffic carried by the host side, a test-signed build. Its listing says exactly that, it is marked as a development tier, and a deployment lands there only if you choose it.

plain · planned

Apps kept apart; no other claim

An ordinary Linux server without a confidential CPU would give each app its own virtual machine and nothing more: the host can read everything, and the listing would say "no TEE CPU". No such host is listed today, and none will be listed without that label.

What we do not claim

No host here is described as unable to see your data unless a confidential processor enforces it and attests it. A confidential processor defends memory against software, not against someone with physical access and lab equipment on the memory bus, and a self-hosted seller does have physical access to their own machine. On a shared confidential host, other tenants are kept out by the sandbox and the operating system, not by a hardware partition. Per-app hardware isolation, one confidential guest per app, has been demonstrated and rechecked in the lab; it is not shipped, and the denser one-plane-per-app shape is still being built. Deploying is two dials, what you rent, and two rates, what you pay. Prepaying buys runtime by the second; the deployment runs until that time is used up, and you top up to extend it. Payments convert straight into runtime, a paid app's publisher share goes straight to the publisher, and payments are final. Unspent time stays on the deployment's public record (stop now, resume later) but is not withdrawable, so fund in small top-ups. The rates below are the ledger's list rates; a host may post its own, and the store shows the rate of the host your deployment would land on. A GPU share can only be bought while a GPU host is attached, and the live fleet panel is the authority on that.
GPU / VRAM dial × $6/hr per full card

0-100% of one GPU card. VRAM and compute move together: each percent buys ≈1.4 GB VRAM and ≈9.9 TFLOPS. 0% = a CPU-only app.

CPU / RAM dial × $3/hr per whole node

0-100% of the node's vCPU+RAM: each percent buys ≈0.16 vCPU, ≈0.64 GB RAM, ≈10 GFLOPS (a whole node is roughly a thousandth of a card's FLOPS). Your app's memory cap is exactly this slice of the node's 64 GB.

Floors come from app specs minimums, not suggestions

The VRAM, compute, and RAM an app declares in the catalog set each dial's minimum: spec ÷ server spec (140.4 GB / 989 TFLOPS per card; 64 GB / ~1000 GFLOPS per node), larger axis wins, rounded up to a whole percent. An app declaring 494 TFLOPS cannot deploy below a 50% GPU share even if it needs 2 GB of VRAM: you cannot occupy an axis without paying for it.

Rules of the road software caps · two independent dials

The two shares are independent: a GPU app may buy more node than card, and a 100%-GPU, 10%-CPU tenant leaves 90% of that node for CPU-only apps. Unsold CPU on a GPU node is never stranded. Shares are runtime-enforced software caps, not hardware partitions.

contract
price = GPU% × $6/hr  +  CPU% × $3/hr  ·  metered per second

One honest rounding note: the per-second rate is settled in whole millionths of a dollar, rounded up, so the very smallest slices meter a hair above the formula (a 1%-CPU app runs at $0.0324/hr rather than $0.0300). Every estimate shown on the deploy pages already includes this. Some store apps also charge a small hourly publisher fee: capped by the platform, shown in the rate before you pay, and paid straight to the app's publisher.

Three words, used the same way on every page: available means a deployment can have it now; experimental means built and measured on a lab machine or one box; planned means designed or intended and not yet run. The short list is here; the Architecture tab under Develop has the full board and evidence.
available

In use today

Wasm apps on confidential Linux hosts · GPU inference inside the confidential VM, on GPU hosts · browser-side verification of the whole chain · on-chain catalog, ledger and publisher fees · custom domains with in-enclave certificates · encrypted volumes, secrets, WAF · TCP, UDP and dedicated IPv6 · self-hosted confidential servers · one Windows host, labeled as a development tier. Which hosts are attached right now is a live panel, not a promise: see what is serving.

experimental

Built, measured, not yet yours to pick

A domain contract shared by every backend · per-app hardware isolation inside the confidential VM, one guest per app, demonstrated in the lab and independently rechecked · a Hyper-V partition per app on Windows · shielded inference on GPUs the enclave does not trust, run on one self-hosted server · permissionless host attach behind a published allowlist.

planned

Designed, not run

Ordinary Linux hosts with one VM per app and no confidentiality claim · one hardware plane per app for density · host exclusion on Windows · publisher-owned signatures, local trust policy, mirrors and peer transports, interchangeable coordinators, independent recovery of secrets and state.
